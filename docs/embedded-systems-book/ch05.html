第5章 中断

Making Embedded Systems — Elecia White 著 | AI 辅助翻译

中断

中断可能令人恐惧。它们是使嵌入式系统不同于传统应用软件的因素之一。中断从无处突然出现，改变代码的流程。它们只能安全地调用某些函数（通常不能调用调试函数）。中断需要很快，快到它们仍然偶尔用汇编语言编写。而且中断中的bug通常很难找到，因为根据定义，它们是异步发生的（在正常执行流程之外）。

然而，中断并不像被描述的那样是可怕的东西。如果你理解中断发生时发生了什么，你会发现它们可以成为你软件设计中有用的部分。

一只鸡按下了按钮

将中断想象成一个鲁布·戈德堡机械¹，其目标是告诉你的软件在正常代码流程之外发生了某事。让我们考虑图5-1中的鸡。

¹ 鲁布·戈德堡机械是一种过于复杂的装置，用来做相对简单的事情。这种机器（真实的和比喻的）通常由一系列简单的、不相关的元素组成，每个元素的动作触发下一个元素的开始，直到目标动作发生。

图5-1. 一只鸡按下按钮，引发一连串动作，最终事件循环中的代码采取行动

鸡按下按钮。中断信号传到处理器。处理器保存它当前的位置，然后查找要调用什么代码。它调用那段代码，该代码做一些事情（可能是设置一个变量）。中断结束，处理器返回到这一切发生之前的位置。正常代码继续运行，但现在有了一个变量变化或其他信号，似乎从无处出现。

让我换种方式来说。首先，我想让你记住，处理器和接口就像软件API（见"阅读数据手册"第46页），而函数指针并不可怕（见侧栏"函数指针没那么可怕"第78页）。在我们逐步了解中断发生时会发生什么时，你需要将这两个概念牢记在心：

第5章：中断

1. 中断请求（IRQ）在处理器内部发生，由外部组件、软件或系统中的故障触发。 2. 处理器保存上下文，包括它在哪里以及局部变量。 3. 处理器在向量表中找到与中断关联的函数。 4. 回调函数运行（即中断服务例程，或ISR，或中断处理程序）。 5. 处理器恢复保存的上下文，返回到中断发生前的点，程序继续运行。

让我们更详细地了解中断处理的过程。然后我们将讨论如何设置这些中断使其按你想要的方式工作。

IRQ发生

有些中断就像小型高优先级任务。一旦它们的ISR完成，处理器恢复它保存的上下文并继续运行，仿佛什么都没发生过。大多数外设中断都是这样的：输入线、通信通道、定时器、外设、ADC（模数转换器）等。

其他中断更像是异常，处理系统故障并且永远不会返回到正常执行。例如，当发生内存错误、除零错误、处理器尝试执行无效指令或电源电平不足以正常运行处理器（欠压检测）时，可能会发生中断。这些错误意味着出现了严重问题，处理器无法正常运行。通常当这种情况发生时，中断会将系统置于无限循环中或重置处理器。

你需要处理的大多数中断更像是任务而不是异常。它们让你的处理器似乎并行地运行多个任务。

通常中断请求发生是因为你已经配置了中断。如果不是你配置的，那么供应商的启动代码可能做了这项工作。虽然对高级语言程序员来说通常是不可见的，但启动代码会配置一些面向硬件的东西（例如设置默认中断，通常是故障中断，以及配置系统时钟）。

对于类似任务的中断，你的初始化代码可以将它们配置为在你指定的条件下发生。具体条件取决于你的处理器。你的处理器用户手册对设置中断至关重要。（更多关于配置的内容见本章后面的"配置中断"第140页，在我们讲解中断本身的各个部分之后。）

IRQ发生

由于处理器各不相同，我将重点介绍STM32F103xx处理器，它的中断处理复杂度处于中等水平（Microchip的ATtiny AVR要简单得多，而TI的MSP430x2xx则更复杂）。

不可屏蔽中断

有些处理器将某些中断定义为非常重要以至于不能被禁用；这些被称为不可屏蔽中断（NMI）。（我想"不可禁用中断"这个说法有点拗口。）

前面提到的处理器故障是NMI的一种形式。通常有一个I/O引脚可以链接到NMI，这通常通向设备上的"开"按钮。这些中断在任何时候都不能被忽略，必须立即处理，即使在代码的关键部分也是如此。

中断优先级

回到我们的"鸡按按钮"例子，我们还没有真正讨论过为什么鸡有一个按钮。假设这个按钮用于发现狐狸时需要通知农场主。假设还有一个定时器中断自动喂鸡。

如果喂食定时器和狐狸按钮恰好同时发生（虽然这不太可能），处理器应该处理哪一个？显然，减少来自捕食者的危险优先于喂鸡。中断可以有不同的优先级。

有些处理器通过外设本身来处理中断优先级（所以定时器1的优先级高于定时器2，而定时器2又比定时器3更重要）。其他处理器允许你按每个中断配置优先级。

嵌套中断

有些处理器允许中断被另一个中断打断。优先级不仅在ISR被调用时重要，还用于确定新中断是否可以抢占当前正在运行的中断。

这是一个强大的工具，但可能会导致不必要的复杂性。除非嵌套中断解决了系统特有的明确问题，否则习惯上在ISR中禁用其他中断。大多数允许嵌套中断的处理器会给你一种在系统初始化时禁用它们的方法。

栈（和堆）

栈是一种以后进先出（LIFO）方式保存信息的数据结构，如图5-2所示。你将数据压入栈（将其添加到栈的内存中，并增加指向下一组数据存放位置的指针）。要取出最后一块数据，你从栈中弹出（这会减少指针）。

图5-2. 栈基础

栈是任何开发者都可以实现的简单数据结构，但"the stack"（带定冠词的栈）指的是系统调用栈，它位于每个正在运行的程序背后，在RAM的指定区域中。对于每个函数调用，编译器会创建一个栈帧，其中包含局部变量、参数以及函数完成后的返回地址。每个函数调用都有一个栈帧，从复位向量开始，然后是main的调用，然后是你在此之后调用的任何内容。（或者如果你有多个线程，每个线程都有自己的栈。）

堆是一种树形数据结构。"the heap"是动态分配内存的来源（之所以这样命名，是因为它可以用堆数据结构来实现）。通常堆向上增长（见图5-3），而栈向下增长。当它们相遇时，你的系统会崩溃。嗯，实际上你的系统可能在它们相遇之前就崩溃了，因为它们之间可能还有其他东西（全局变量、静态变量，可能还有代码）。（更多内容见第11章。）

如果栈变得太大，它可能会增长到其他内存区域，例如全局数组所在的位置。如果栈覆盖了数组的内存，数组中损坏的数据很可能会给你错误的结果。这被称为栈溢出。

另一方面，如果全局数组覆盖了栈，函数返回地址可能会被损坏。当函数返回时，程序将返回一个虚假地址并崩溃（通常是由于不合适的指令）。

保存上下文

中断请求发生后，处理器在找到适当的函数处理程序之前保存它所在的位置。就像书签保存你的阅读位置一样，处理器将上下文保存到栈中；见"栈（和堆）"第129页。上下文包括程序计数器（指向下一条要执行的指令）和处理器寄存器的一个子集（这些寄存器就像处理器自己的缓存局部RAM）。寄存器内容被保存，以便中断代码可以在执行中使用它们，而不会破坏主代码路径的状态。

这些步骤不是免费的。从IRQ到ISR所花费的时间是处理器的中断延迟，通常在用户手册中宣传为需要一定数量的处理器周期。

第5章：中断

系统延迟是从中断事件发生到ISR开始的最坏情况时间量。它包括处理器的中断延迟和中断被禁用的最长时间。

如果不允许中断嵌套，则在处理中断时新中断被禁用。系统延迟的最大贡献者可能是在最长中断中花费的时间。保持中断简短！

中断延迟的处理器周期是损失的。如果你有一个每秒可执行一百条指令的处理器（100 Hz），中断延迟为10个周期，并且你设置了一个每秒中断一次的定时器，你将因上下文切换损失10%的周期。实际上，由于你还必须恢复上下文，情况可能更糟。尽管10个周期是一个不错的中断延迟（不算很好，但也不差），但100 Hz的系统很少见。然而，用30 MHz处理器来计算，在一个44,100 Hz的中断中处理音频，10周期延迟仅仅调用中断处理程序就使用了处理器1.47%的周期。这甚至还不包括执行ISR或从中返回的时间。

处理器设计者致力于保持低中断延迟。一种方法是存储最小量的上下文。这意味着处理器不会保存所有处理器寄存器，而只保存一个子集，要求软件存储它需要的其他寄存器。这通常由编译器处理，但会增加有效的系统延迟。

计算系统延迟

在中途中调用大量函数是不鼓励的。每个函数调用都有一些开销（在第11章中更详细地讨论），因此函数调用会使你的中断花费更长的时间。如果你在中途中禁用了其他中断，你的系统延迟会随着每个函数调用而增加。

随着系统延迟的增加，其处理实时事件的能力会下降。考虑前面提到的30 MHz处理器和44,100 Hz中断。如果每个中断使用10个周期用于中断开销，10个周期用于调用五个短函数（每个），这些函数共使用275个周期实际处理信息，则在至少335个周期（10 + 5 × 10 + 275）内不能处理其他中断。这消耗的时间是11 μs（335/30 MHz）。还要注意，系统将近50%的时间花在中断中（44,100 Hz × 11微秒 = 0.492秒）。减少中断的开销将为其他任务释放处理器周期。

从向量表中获取ISR

在IRQ发生并保存上下文之后，处理中断的第三步是通过查找中断向量表（IVT）来确定调用哪个ISR。此表位于处理器内存的特定区域。当中断发生时，处理器在表中查找与该中断关联的函数。

IVT是一个回调函数列表，每种中断类型对应一个。秘密地说，向量表是一个函数指针列表，尽管其代码通常用汇编语言实现。

初始化向量表

启动代码（可能随编译器或处理器供应商HAL一起提供）为你设置了向量表，通常带有占位中断处理程序。在调试时，你可能希望未处理的中断进入无限循环，这样你就能发现它们，然后关闭中断或正确处理它。

当产品上市时，让未处理的中断处理程序进入无限循环会导致系统无响应。你可能希望未处理的中断简单地返回正常执行。这会浪费处理器周期，仍然是一个bug，但至少该bug对客户的影响是轻微变慢，而不是系统需要重启。

在某些情况下，如果你将处理程序函数命名为与表中的相同，某些工具的魔法会让链接器在IVT中使用你的函数。然而，对于其他处理器和编译器，你需要将你的ISR插入到函数表中中断的正确槽位。

在STM32F103xx处理器中，使用STM32Cube HAL，我们只需要将ISR命名为TIM2_IRQHandler，链接器就会将正确的函数地址放入向量表。在一些处理器中，例如Microchip的AT91SAM7S，你必须创建一个函数并手动将其放入表中：

interrupt void Timer1ISR(){ … } void FoodTimerInit(){ … AT91C_BASE_AIC->AIC_SVR[AT91C_ID_TC1] = // 在IVT中设置TC1 IRQ

// 处理程序地址

(unsigned long)Timer1ISR; // 源向量寄存器， // 槽位 AT91C_ID_TC1 (12) … }

查找ISR

向量表位于内存中的特定地址，由链接器脚本设置。由于这可能在启动代码中已为你完成，你通常不需要知道如何做。然而，如果你好奇，让我们深入了解一下STM32F103xx的启动代码：

__attribute__ ((section(".isr_vector"))) void (* const g_pfnVectors[])(void) = {

// Core Level - CM3

&_estack, // 初始栈指针

Reset_Handler, // 这是运行的最开始

NMI_Handler, // 不可屏蔽故障处理程序

…

TIM2_IRQHandler, // 28, TIM2全局中断

TIM3_IRQHandler, // 29, TIM4_IRQHandler, // 30, … }

列表中的第一行是一条非标准行，它告诉编译器以下变量需要放在某个特殊位置，链接器脚本将指示这个位置在哪里（在.isr_vector指定的位置）。我们稍后会更多地讨论链接器脚本（见"链接器脚本入门"第257页），但现在可以放心地说，.isr_vector链接器变量位于用户手册所说的向量表应处的位置（0x00000000）。

在void *元素数组内部，有栈的位置，同样在链接器脚本中设置。之后是复位向量，即系统启动或因其他原因复位时调用的代码地址。它是前面提到的异常中断之一。大多数人不会把打开电源或按下复位按钮视为对其代码的中断。然而，处理器通过从表中加载一个向量来响应复位，就像它通过加载一个向量来响应中断一样。在表的后面，有外设中断，例如我们的定时器。图5-4显示了这在处理器内存中的样子。

每个中断都有一个中断号。对于我们的定时器3中断，它是50。当中断发生时，它仅通过这个号码来发出信号，生成IRQ的处理器部分将其发送到处理器中负责在向量表中按号码查找处理程序的部分。处理器使用中断号和向量表的结构来查找中断到达时要调用的地址。

可重入函数

可重入函数是指可以在运行时被安全地多次调用的函数。例如，下面这个普通的swap函数是不可重入的，因为它有一个临时变量t，其值在使用它设置最终y变量之前不能改变：

int t; void swap(int* x, int* y) { t = *x; *x = *y; // 硬件中断可能在此处调用 isr()，而

// 该函数被 main 或其他非中断代码调用

*y = t; } void isr { int x=1, y=2; swap(&x, &y); }

使用静态变量或全局变量的函数是不可重入的。许多 C++ 对象因其私有数据而本质上是不可重入的。更糟糕的是，一些标准库调用也是不可重入的，包括 malloc（或 new）和 printf（任何 I/O 或文件函数）。 当系统保存上下文时，它只做最基本的保存工作。编译器可以做得更多，但即便如此，也不会给你一个完全干净的环境来操作。这其实是一件好事，因为你通常需要一两个全局变量来向非中断代码发出中断已发生的信号。然而，在编写 ISR 时，对于使用了全局变量却没有对中断进行保护的函数，你必须格外警惕。

请做好中断在最糟糕的时刻发生的准备。这样，你才能设计出能够最大限度减少其破坏性的系统。

调用 ISR

到目前为止，我们已经了解了 ISR 的工作原理以及如何设置它。现在，我们将进入实际 ISR 的核心部分——你需要实现的部分。我们已经看到了围绕 ISR 最重要的规则： • 保持 ISR 简短，因为较长的 ISR 会增加系统延迟。通常应避免函数调用，因为函数调用可能有隐藏的深度并增加开销。 • 不要调用不可重入的函数（例如 printf），因为全局变量可能被中断破坏。 这为我们实现 ISR 提供了设计指南。我们的定时器中断很容易实现，因为我们需要做的只是设置一个标志，指示到了喂鸡的时间：

volatile tBoolean gFeedChicken= FALSE; // 中断处理程序设置的全局变量，

// 当事件被处理后由普通代码清除

void TIM2_IRQHandler(void){ __disable_irq();

// 禁止中断嵌套

gFeedChicken = TRUE; __enable_irq(); }

该中断不输出调试信息，也不驱动喂食机构。尽管这样做似乎很合理，但保持中断简短意味着我们需要让系统的其他部分来处理这些事情。这样可以最大限度地降低系统延迟。 中断不仅仅能设置标志和解除通信驱动程序的阻塞。添加更长的代码以使系统更安全，是值得做出的权衡。除此之外，请保持中断简短！ 许多处理器要求你确认（或清除）中断。通常这是通过读取状态寄存器来完成的。如第 136 页"编写间接寄存器"中所述，这可能会产生清除该位的副作用。

编写间接寄存器

内存映射寄存器可能具有一些有趣的特性。寄存器并不总是像变量那样运作。 如果你想修改一个普通变量，隐藏在你的 memoryReg |= 0x01 这行代码背后的步骤如下：

1. 将内存的当前值读入处理器寄存器。 2. 修改该值。 3. 将变量写回内存。

然而，对于设置中断处理的寄存器来说，如果在上述任意两个步骤之间发生中断，这个多步骤过程就可能产生问题。为了防止这种竞态条件——即中断在状态不一致时发生——对寄存器的操作必须是原子的（在单条指令中执行）。 这是通过一组间接寄存器来实现的：一个可以设置位的寄存器和一个可以清除位的寄存器，它们各自作用于第三个功能寄存器，而该功能寄存器可能无法直接写入（也不是内存映射的）。要间接设置一个位，你必须在设置寄存器中写入该位。要间接清除一个位，你在清除寄存器中写入该位。在任一寄存器（设置或清除）中，未设置的位不会对功能寄存器产生任何影响。（图 5-5 的 B 部分给出了设置和清除位以及每一步功能寄存器内容的示例。） 有时功能寄存器会反映在设置和清除寄存器中，因此如果你读取其中任何一个，你都可以看到当前设置的位。不过，读到与你写入同一个寄存器的内容不一致的值，可能会令人困惑。 功能寄存器也可能是只写的，没有任何读取方式。一些处理器通过让一个寄存器在写入时充当功能寄存器、读取时充当状态寄存器来节省内存空间。在这种情况下，你需要使用影子变量来跟踪功能寄存器中设置的位——影子变量是你代码中的一个全局变量，每次修改寄存器时你也修改它。你将需要修改你的影子变量，然后用影子变量的值写入寄存器，而不是操作设置和清除中间寄存器。 还有一些寄存器，读取该寄存器的行为会修改其内容。这通常用于状态寄存器，一旦你的代码读取该寄存器，处理器就会清除挂起的状态（参见图 5-5 的 C 部分）。这可以防止在用户读取寄存器和清除相关位之间的时间窗口内发生竞态条件。 你的用户手册会告诉你哪些类型的寄存器表现出特殊行为。

在你的 ISR 完成后，就该返回到正常执行了。一些编译器扩展了 C/C++，包含了 interrupt 关键字（或 __IRQ，或 _interrupt）来指示哪些函数实现了中断处理程序。处理器对这些函数给予特殊处理，无论是在它们启动时（在 ISR 开始运行之前保存部分上下文）还是在它们返回时。 如第 130 页"保存上下文"中所述，程序计数器指向你即将执行的机器指令。当你调用一个函数时，下一条指令的地址（程序计数器 + 1 条指令）被放入栈中作为返回地址。当你从函数返回（rts）时，程序计数器被设置为该地址。

不同的汇编语言有相似的操作码并不奇怪。然而，rts 和 rti 往往是非常通用的。它们分别代表"从子程序返回"（ReTurn from Subroutine）和"从中断返回"（ReTurn from Interrupt）。

然而，中断并不是一个标准的函数调用；它是由处理器引起的跳转到中断处理程序的操作。如果中断像普通函数一样返回，那么处理器为保存上下文所做的那些操作就不会被撤销。因此，中断有一个特殊的汇编指令（rti）来指示它们正在从中断返回。这让处理器知道，在继续执行之前，它必须将上下文恢复到函数调用之前的状态。 如果你的 C/C++ 编译器不要求你指示某个函数是中断，你可以放心，它一定通过其他方式实现了从中断返回。也就是说，编译器可能将中断函数包装在汇编代码中，该汇编代码仅仅调用你的函数。一旦你的处理程序从函数调用返回，汇编包装器就从中断返回。处理器将栈恢复到原来的状态，程序从它离开的精确位置继续执行。 直到鸡再次按下按钮。

何时使用中断以及何时不使用中断

现在我们已经将鸡的喂食定时器设置为使用中断，并创建了处理中断的代码，但我们需要回过头来重新思考。我们遗漏了一个设计步骤：喂食超时应该是一个中断吗？ 在许多情况下，最简单的解决方案就是中断。通信通路通常有需要填充（或清空）的缓冲区。中断可以作为后台任务来填充缓冲区，而前台任务则生成（或使用）数据。输入线上的变化如果需要快速处理，可能需要中断。处理线上变化的实时性要求越高，中断就越适合作为解决方案。此外，如果检查中断类型事件是否发生会占用其他活动的时间，那么使用中断更好。 我们也看到了中断有一些严重的缺点。我已经提到过每个中断的开销，如果你有很多中断，这些开销会累积起来。中断还会使你的系统变得不那么确定性。没有操作系统² 的一大好处是，你可以说一旦指令 x 发生，y 就会发生。如果你有中断，你就会失去系统的可预测性。而且，由于代码不再是线性流程，调试更加困难。更糟糕的是，如果某些灾难性 bug 依赖于中断在代码中非常特定的时间发生（即竞态条件），它们将非常难以追踪。此外，配置在很大程度上依赖于编译器和处理器（实现也可能如此），因此中断往往使你的代码可移植性降低。 归根结底，实现（和维护）中断的开发成本相当高，有时甚至比找出不使用中断解决问题的方法还要高。把中断留给当你需要它们特殊能力的时候：当系统是时间关键的、当某个事件检查成本高昂且很少发生、以及当一个简短的后台任务能让系统运行得更流畅时。

² 一些实时操作系统（RTOS）是确定性的，通常是较昂贵的那些。

轮询 反复问一个人"你好了没有？"通常在第四次或第五次之后就认为是不礼貌的，但处理器并不在意代码是否不停地询问某个事件是否就绪。轮询会增加处理器开销，即使在没有事件需要处理时也是如此。然而，如果你本来就要处于一个 while 循环中（即空闲循环），那就没有理由不检查事件。 轮询编码很简单。有一个细微之处值得一提：如果你正在轮询并等待硬件完成某项操作，你可能需要设置一个超时，以防你恰好错过了事件或者硬件没有正确接收你的命令。 对于喂鸡来说，我们只需要等待一定的时间过去。尽管嵌入式系统以速度快著称，但许多系统将其大量的时钟周期花在了等待时间流逝上。

void SchedulerRun(tTime now);

当调度器运行时，它遍历其任务列表。找到启用的任务后，它检查当前时间是否晚于 runNextAt。如果是，则通过调用回调函数来运行该任务。SchedulerRun 函数位于主循环中，在没有其他事情可做时运行。 这些任务不是中断级别的，因此不应用于具有实时约束的活动。此外，任务必须礼貌且相对快速地交出控制权，因为它们不会像在典型操作系统中那样被抢占。 调度器还有最后一个部分：将任务附加到调度器以使它们运行。首先，你需要分配一个任务。接下来，用你的回调函数、函数应该运行的时间以及每次后续运行之间的时间间隔（对于周期性函数）来配置它。最后，将其发送给调度器以放入其列表中：

发布/订阅模式

通过调度器，我们构建了所谓的发布/订阅模式（也称为观察者模式或 pub/sub 模型）。调度器发布已经过去的时间量，而多个任务（以不同的时间间隔）订阅该信息。这种模式可以更加灵活，通常发布多种不同类型的信息。 该模式的名称来源于报纸，这可能是记住它的最简单方式。你代码中的一部分发布信息，而代码的其他部分订阅它。有时订阅者只请求信息的一个子集（就像只订阅周日版）。发布者与

面试问题：不该问什么

你知道什么好笑的笑话吗？

我喜欢糟糕的笑话。但这是一个糟糕的面试问题。它不像询问种族、宗教、性别、年龄、原籍国、婚姻状况、残疾等问题那样糟糕。在美国，上述许多问题是违法询问的。比违法更糟糕的是，这类问题是不专业的。 面试的目标是确定应聘者是否能胜任这份工作，以及你能否与他们共事。 很多时候，我们招聘的目标是再雇一个"我"，这样我就能少做些工作。如果你能直接雇一个我的克隆人，事情会更快：说同一种语言、有相同的文化背景（因此能理解习语和内部笑话）、使用相同的参考框架。 这是短视的。虽然你可能完全出色，但从长远来看，多样性通过为问题提供更多的视角而带来巨大的回报。 我们需要争论者和调解者，我们需要直线思维的人和绕圈子或跳跃思维的人，我们需要在不同"便宜"观念下长大的人、以光速前进的人，以及能确保他们方向正确的人。
