第6章 管理活动流程

Making Embedded Systems — Elecia White 著 | AI 辅助翻译

管理活动流程

在第 2 章中，我们探讨了将系统分解为可管理模块的不同方法。那一章描述了设计的内容和原因；本章则涵盖实现的方法。一旦你确定了各个部分，让它们作为一个系统协同工作可能会令人生畏。

调度与操作系统基础

在没有操作系统的情况下构建嵌入式系统，需要理解操作系统能为你做的一些事情。我只会给出简要的概述；如果本节中的任何内容对你来说是全新的，你可能需要回顾一本关于操作系统的书籍（参见第 177 页"延伸阅读"）。

任务 当你打开电脑时，如果你和我一样，你会加载电子邮件客户端、网页浏览器和编译器。还有其他几个程序会自动启动（比如我的日历）。这些程序中的每一个都在计算机上运行，看起来是并行的，即使你只有一个处理器。 有三个词含义略有不同但大量重叠，有时会被互换使用。虽然这些定义是我学到的，但有些 RTOS 可能会将它们调换。任务是处理器所做的事情。线程是一个任务加上一些开销，比如内存。进程通常是一个完整的执行单元，拥有自己的内存空间，通常与其他进程分开编译。我重点讨论任务；线程和进程通常意味着操作系统的存在。

你正在运行的操作系统有一个调度器，它在活跃的进程（或线程）之间进行切换，让每个进程按适当的顺序运行。实现调度器的方法有很多，这个话题远远超出了本书的范围（更不用说这一小节了）。关键点是调度器了解你的系统应该执行的所有任务/线程/进程/事物，并选择现在执行哪一个。 在没有操作系统的情况下，你需要自己管理调度。最简单的调度器只有一个任务。就像第 4 章中闪烁 LED 的项目一样，你可以每次做同样的事情（亮、等待、灭、等待、重复）。然而，当系统对环境中的变化做出反应时（例如，改变 LED 时序的按钮按下），事情会变得更加复杂。

任务之间的通信

按钮按下中断和 LED 闪烁循环是我们一直在研究的小型系统中的两个任务。当我们使用一个全局变量来指示按钮状态已改变时，这两个任务彼此进行了通信。然而，在任务之间共享内存是危险的；你必须小心操作方式。 图 6-1 显示了事件的正常过程：当按钮被按下时，中断设置共享内存。然后主循环读取并清除该变量。用户再次按下按钮，导致中断再次设置该内存。 假设就在主循环清除变量时，中断再次触发。在变量被清除的同一瞬间，中断停止处理，冲进来设置该变量。它最终是设置状态还是清除状态？ 答案取决于发生的精确时序。这种不确定性是一个大问题。如果对于一个简单的布尔值都可能如此复杂，那么考虑一下如果代码需要设置两个变量或整个数据数组，会发生什么。 这种关于实际将发生什么的不确定性被称为竞态条件。任务之间共享的任何内存都可能表现出这种不确定性，导致不稳定和不一致的行为。

调度与操作系统基础

避免竞态条件

我们需要一种方法来禁止多个任务写入同一内存。不仅写入可能成为问题；主循环既读取指示按钮已改变的变量，也读取按钮的值。如果在这两次读取之间发生中断，它可能会改变按钮的值。 每当任务之间共享的内存被读取或写入时，就会产生临界区代码，即访问共享资源（内存或设备）的代码。共享资源必须受到保护，以便一次只有一个任务可以修改它。这被称为互斥（mutual exclusion），通常简称为 mutex。互斥锁有时通过信号量、邮箱或消息队列来实现。 在有操作系统的系统中，当两个任务都在运行且都不是中断时，你可以使用互斥锁来指示哪个任务拥有某个资源。这可以简单到一个变量，指示该资源（或全局变量）是否可供使用。然而，当其中一个任务是中断时，我们已经看到连布尔值都不安全，因此这种资源所有权的变更必须是原子的。原子操作是指不能被系统中任何其他事物中断的操作。 从这里开始，我们将重点讨论任务可被中断但除此之外一直运行直到交出控制权的系统。在这种情况下，避免竞态条件的方法是在访问共享全局变量时禁止中断。但这有一个缺点：当你关闭中断时，系统对按钮按下的响应速度会变慢，因为它必须等待退出临界区。关闭中断会增加系统延迟（响应所需的时间）。 在我们讨论实时系统时，延迟很重要。实时系统必须在固定的时间内响应事件。虽然所需的响应时间取决于系统，但通常以微秒或毫秒为单位。随着延迟的增加，系统注意到事件所需的时间增加，因此事件与其响应之间的总时间也增加。

优先级反转

一些处理器允许中断具有不同的优先级（就像操作系统对进程和线程所做的那样）。虽然这种灵活性非常有用，但它也可能给你带来很多麻烦。图 6-2 显示了典型操作系统对优先级反转的定义。高优先级进程因为需要访问低优先级进程持有的资源而停止，这是可以接受的。然而，如果一个中优先级进程启动，它可能会阻塞低优先级进程完成对高优先级任务所需资源的使用。中优先级任务阻塞了高优先级任务。

例如，假设我们有高优先级的按钮按下中断和低优先级的主循环。当主函数访问按钮按下变量时，它关闭按钮按下中断以避免竞态条件。之后，我们添加了另一个中断，用于通过通信端口输出调试数据。这应该是一个中优先级的后台任务，是应该完成但不应该阻塞系统处理按钮按下的事情。然而，如果调试任务中断了主循环，它就正好做了这件事。 处理器最应该做的是什么？那应该是最高优先级的。如果有人问调试输出是否比按钮按下更重要，我们会说不是。如果是这样，为什么处理器在运行调试中断而不是按钮处理程序？在这种情况下，简单的修复方法是在按钮中断发生时禁用所有中断（或所有优先级低于按钮处理程序的中断）。 在我们探讨没有操作系统的不同任务管理方式时，要警惕那些导致处理器不经意地运行非最高优先级任务的情况。

状态机

在你有不止一件事情在进行的情况下，保持系统有序的一种方法是

on 是使用状态机。这是一种标准的软件模式，嵌入式系统大量使用它。根据《设计模式：可复用面向对象软件的基础》一书，状态模式的意图是"允许一个对象在其内部状态改变时改变其行为。该对象看起来像是改变了它的类。"

更简单地说，当你调用一个状态机时，它会根据其当前状态做它认为应该做的事。它不会每次都做同样的事情，而是会根据其上下文来改变行为，上下文包括环境和状态机的历史（内部状态）。如果这些听起来过于学术化和理论化，还有一种更简单的理解状态机的方式：流程图。

几乎任何状态机都可以用流程图来表示。（反过来，你用流程图解决的问题很可能注定会变成一个状态机。）状态机也可以用有限状态自动机来表示（如图 6-3 所示），其中每个状态是一个圆圈，状态之间的变化（状态转换）是一个箭头。

图 6-3. 交通灯系统

我们将在下一节中详细审视图中的每个元素。图中的箭头和圆圈同样重要。状态机不仅关乎系统可以处于哪些状态，也关乎系统要处理哪些事件。

状态机示例：交通灯控制器

为了恰当地讨论状态机，我们需要一个比闪烁 LED 和按钮稍微复杂一点的例子。图 6-3 展示了一个交通灯控制器。

当灯是红色且控制器收到通行消息时，它将灯变为绿色。当控制器收到停止消息时，它将灯变为黄色一段时间，然后变为红色。我们这样实现了这个交通灯，只要没有人需要它改变，它就保持绿色。可以推测，当有车辆到达交叉路口时，就会产生停止命令。

有一个状态转换——即每个箭头所表示的形式化术语——稍微有些微妙。当灯是黄色且控制器收到通行消息时，它不应该将灯变回绿色。黄灯应该变为红灯，而不是绿灯，所以通行消息只是让灯保持在黄色阶段。这种微妙性正是状态机会给你带来的陷阱之一。你必须为每个状态下可能发生的每个事件做好准备，包括非常罕见的情况——甚至那些不该发生但可能因错误而发生的情况。

要使用状态机，首先要弄清楚状态以及可以改变状态的事件。对于这样一个简单的系统，画图是最好的方法。一旦你确定了状态（红、黄、绿），就看看它们之间的连接。停止和通行命令应该只分别在绿色和红色状态下发生。即便如此，这些命令是异步的，来自系统外部，所以每个状态都应该能够处理它们，即使它们在不合适的时候出现。这里处理不当命令的最简单方法是忽略它们，画一个回到关联状态的循环。

如果不当事件发生，可能更好的做法是生成某种错误。运用你的判断力。

状态为中心的状态机

大多数人将状态机想象成一个大的 if-else 语句或 switch 语句：

while (1) {

look for event

switch (state) { case (green light): if (event is stop command)

turn off green light

turn on yellow light

set state to yellow light

start timer

break; case (yellow light): if (event is timer expired)

turn off yellow light

turn on red light

set state to red light

break; case (red light): if (event is go command)

turn off red light

turn on green light

set state to green light

break; default (unhandled state)

error!

} }

这里状态机的形式是：

case (current state):

if event valid for this state

handle event

prepare for new state

set new state

状态机可以改变其上下文（转移到新状态）。这意味着每个状态都需要了解其兄弟状态。

带隐藏转换的状态为中心的状态机

另一种实现状态机的方法是将状态转换信息与状态机分离。这在理论上比前一节的模型更好，因为它有更多的封装和更少的依赖。之前的模型迫使每个状态知道如何以及何时触发从它可达的每个其他状态。在本节我将展示的模型中，某个更高层的系统跟踪哪个状态到达哪个其他状态。我将其称为"下一个状态"函数。它处理每个状态，并将系统置于它应该处于的下一个状态。通过创建这个函数，你可以将每个状态中执行的动作与状态转换分离开来。

其通用形式如下：

case (state): make sure current state is actively doing what it needs

if event valid for this state

call next state function

在交通灯示例中，这个模型会为每个状态创建更简单的代码，而且几乎所有状态都很相似。例如，绿灯状态会像这样：

case (green light): turn on green light (even if it is already on) if (event is stop)

turn off green light

call next state function

break;

当发生变化时应该调用下一个状态函数。代码与前一节中的类似，因为它也是一个简单的 switch 语句：

next state function: switch (state) { case (green light):

set state to yellow light

break; case (yellow light):

set state to red light

break; case (red light):

set state to green light

break; }

现在你有一个地方查看状态，另一个地方查看转换，但每个都很简单。在这个例子中，状态转换独立于事件，这是表明这是一个良好实现方法的线索。

这个模型并不总是最好的。例如，如果黄色状态下的通行命令导致回到绿色，那么下一个状态函数将同时依赖于当前状态和事件。这种方法的目标是隐藏转换，而不是混淆你的代码。有时候最好将它们全部放在一起（如"状态为中心的状态机"一节所述）。

事件为中心的状态机

另一种实现状态机的方法是翻转过来，让事件控制流程。使用这种方法，每个事件都有关联的一组条件语句：

case (event):

if state transition for this event

go to new state

例如：

switch (event) case (stop): if (state is green light)

turn off green light

go to next state

// else do nothing

break;

大多数状态机在 switch 语句和状态之间形成了舒适的匹配，但在某些情况下，将状态机与事件关联起来可能更清晰，如下所示。函数可能仍然需要一个 switch 语句来处理对当前状态的依赖：

function to handle stop event

if (state == green light)

turn off green light

go to next state

与以状态为中心的选项不同，以事件为中心的状态机实现可能会使内务活动（例如检查黄色状态的超时）变得困难。如果你的系统需要定期维护，你可以将内务设为一个事件，或者你可以坚持使用前一节中展示的以状态为中心的实现。

状态模式

一种面向对象的实现状态机的方法是将每个状态视为一个对象，并在对象中创建方法来处理每个事件。我们示例中的每个状态对象将具有以下成员函数：

Enter

当进入状态时调用（打开其灯） Exit 当离开状态时调用（关闭其灯）

EventGo

根据状态适当处理通行事件

EventStop

处理停止事件

Housekeeping

定期调用，让状态检查变化（如超时）

一个更高层的对象——上下文——跟踪状态并调用适当的函数。它必须为状态提供一种指示状态转换的方式。如前所述，状态可能互相了解并适当选择，或者转换可能被隐藏，因此状态可能只指示需要转到下一个状态。我们的系统很简单，所以一个简单的下一个状态函数就足够了。用伪代码表示，类如下：

class Context {

class State Red, Yellow, Green; class State Current; constructor: Current = Red; Current.Enter(); destructor: Current.Exit(); Go: if (Current.Go() indicates a state change) NextState(); Stop: if (Current.Stop() indicates a state change) NextState(); Housekeeping: if (Current.Housekeeping() indicates a state change) NextState(); NextState: Current.Exit(); if (Current is Red) Current = Green; if (Current is Yellow) Current = Red; if (Current is Green) Current = Yellow; Current.Enter(); }

允许每个状态被完全相同地对待，使系统摆脱了 switch 语句，让对象完成以前由条件语句完成的工作。

表驱动状态机

虽然流程图和状态图对于构思状态机很方便，但记录和完全定义状态机的一个更简单的方法是使用表格。

在图 6-4 的示例表格中，每个状态有一行，包含一个动作和多个事件。动作列描述了在该状态下应该发生什么（哪个特定的灯应该亮起）。其他列显示了当系统处于某个状态且某个事件发生时需要进行的转换。通常，转换只是转移到新状态（并执行新关联的动作）。

图 6-4. 作为数据表的状态机

当我在儿童玩具领域工作时，它们通常提供 30 个或更多的按钮（字母、音量、控制等）。像这样的表格帮助我们找出流程图中哪些事件没有被处理。即使一个按钮在某个状态下可能无效，总有人会莫名其妙地按下它。所以这样的表格不仅有助于实现和文档记录，它们对设计游戏玩法也至关重要。

将系统定义为表格，暗示着可以在代码中将其定义为数据表。你最终得到的不是一个庞大复杂的代码片段，而是更小、更简单的部分：

• 一个数据表，显示在某个状态下执行的动作以及在事件发生时要转到哪个状态 • 一个引擎，读取数据表并按其指示执行

最棒的是引擎是可复用的，所以如果你要实现许多复杂的状态机，这是一个很好的解决方案。

交通灯问题对于实现来说有点太简单，使得这种方法不太值得，但它是一个直接的例子。让我们从每个表中的信息开始：

struct sStateTableEntry {

tLight light; // 所有状态都有关联的灯

tState goEvent; // 当通行事件发生时要进入的状态

tState stopEvent; // ...当停止事件发生时

tState timeoutEvent; // ...当超时发生时

};

除了每个表的下一个事件外，我还加入了与当前状态关联的灯，这样每个状态就可以被完全相同地处理。（当有许多非常相似的状态时，这种状态机方法才真正发挥作用。）将灯放在状态表中意味着我们的事件处理程序对每个状态做同样的事情：

// 事件处理程序

void HandleEventGo(struct sStateTableEntry *currentState){ // 关闭灯（除非我们要立即重新打开它） if (currentState->light != currentState->go.light) { LightOff(currentState->light); } currentState = currentState->go; LightOn(currentState->light); StartTimer(); }

实际的表格呢？它需要先在数据表中定义一个顺序：

typedef enum { kRedState = 0, kYellowState = 1, kGreenState = 2 } tState; struct sStateTableEntry stateTable[] = { { kRedLight, kGreenState, kRedState, kRedState }, // 红 { kYellowLight, kYellowState, kYellowState, kRedState }, // 黄 { kGreenLight, kGreenState, kYellowState, kGreenState }, // 绿 }

输入这个表格很痛苦，而且容易因差一错误而陷入麻烦。然而，如果你的状态机是一个电子表格，并且你可以将其保存为逗号分隔或制表符分隔的变量文件，一个小脚本就可以为你生成表格。将你的状态机重新组织为电子表格，感觉有点像作弊，但当状态和事件的数量很大时，这是一个强大的技术。

将状态机制作成表格可以创建一个密集的信息视图，让你一目了然地看到整个状态机。这不仅会帮助你发现漏洞（未处理的状态/事件组合），还会让你看到产品是否一致地处理事件。

表格还可以展示更复杂的交互，详细说明需要发生什么。然而，随着复杂性的增加，表格失去了简单地变为数据的能力，它可能需要回到前面展示的、面向控制流语句的实现机制之一。例如，如果我们为交通灯添加一些细节和错误检测，我们会得到一个更复杂的画面：

状态/事件 红 黄 绿

命令：通行 转移到绿色 不清除事件（推迟到红色处理） 什么都不做

命令：停止 什么都不做 什么都不做 转移到黄色，设置定时器

选择状态机实现

我展示的每种状态机选项都提供相同的功能，尽管实现方式不同。我更喜欢表驱动的状态机。我不仅可以复用驱动通用状态机引擎的代码，而且我发现封装的状态使测试更容易。

如果你将上下文与状态分开，单元测试可以调用每个状态函数。如果状态中需要上下文，单元测试可以传入一个上下文信息结构，并在状态相关代码运行后验证上下文的任何更改。用单元测试验证每个状态的功能可以产生更健壮的代码。你可以用任何实现方式做到这一点，只要保持状态封装，以便测试代码可以调用状态，理想情况下不需要知道上下文（或让上下文作为结构传入状态）。

当你考虑你的实现时，要懒惰一些。选择代码量最少的选项。如果它们都差不多，选择复制代码最少的那个。如果一个实现让你可以不复制代码而复用一段代码，那对你的系统来说是更好的实现。如果这仍然不能帮助你选择，考虑哪种形式的代码最容易被他人阅读。

状态机之所以强大，是因为它们让你的代码根据其历史（状态）和环境（事件）来行动。然而，由于它们根据这些因素做出不同的反应，它们可能非常难以维护，导致意大利面条式代码以及状态之间的依赖关系，这些依赖对普通观察者来说并不明显。另一方面，没有更好的方法来实现响应式系统，没有哪种方法能让固有的复杂性更容易维护。文档是关键，这就是为什么我在这些节中先关注状态机的人类可读表示，然后才展示代码实现。

看门狗

我们在调度器一节的开始提到了闪烁红色状态。它的目标是在系统故障发生时将系统置于安全模式。但我们如何知道系统故障已经发生了呢？

我们的软件可以监控自上次通信以来经过了多长时间。如果它在不合理长的时间内没有看到停止或通行命令，它可以做出相应的响应。比喻地说，它充当看门狗来防止灾难性故障。实际上，看门狗这个词在嵌入式领域有更具体的含义。

大多数处理器或复位电路具有看门狗定时器功能，如果处理器未能执行某个动作（例如翻转 I/O 线或写入特定寄存器），它将复位处理器。看门狗系统等待处理器发送一切正常的信号。如果这样的信号在合理（通常可配置）的时间内没有出现，看门狗将导致处理器复位。

目标是当系统故障时，它以安全的方式故障（故障安全）。没有人希望系统故障，但我们必须现实一些。软件会崩溃。即使安全关键软件也会崩溃。在我们设计和开发系统时，我们努力避免崩溃。但除非你是全知全能的，否则你的软件会以意想不到的方式失败。宇宙射线和松动的电线确实会发生，许多嵌入式系统需要自力更生。它们不能等待有人在软件挂起时重新启动系统。它们甚至可能没有被人类监控。如果系统无法从某些类型的错误中恢复，通常最好重新启动并将系统置于良好状态。

使用看门狗并不能让你免于处理正常错误；它仅用于重新启动原本无法恢复的系统。有一些使用看门狗的方法可以使其更有效。但首先，让我们看看一些基于本章前面模型的不太理想的技术，这些技术会使看门狗的效果降低：

设置一个定时器中断，其触发频率略高于看门狗到期的频率

如果你在定时器中断中服务看门狗，你的系统永远不会复位，即使你的系统陷入了无限循环。这违背了看门狗的目的。绝对不要这样做。

设置延时函数（DelayMs）来服务看门狗，理由是处理器在那时没有做其他事情

你的代码中会散布延时函数，所以看门狗会经常被服务。即便如此，如果处理器卡在恰好有延时的代码区域中，系统将不会按预期复位。

将看门狗服务放在处理器需要花费较长时间执行的地方，可能是五个或六个运行时间最长的函数中

通过将看门狗代码散布在各处，它削弱了看门狗的能力，并提供了代码可能在其中一个区域崩溃并挂起系统的可能性。

看门狗的目标是提供一种方法来确定系统的任何部分是否已经崩溃。理想情况下，看门狗服务只在一个地方——一个代码必须经过的地方，表明其所有子系统都在按预期运行。通常，这是主循环。即使这意味着你的看门狗需要有更长的超时时间，让它监视整个系统比给它更短的恢复时间而只监视系统的一部分要好。

遗憾的是，对于某些系统，看门狗无法如此整齐地隔离。当必须向看门狗发送信号的代码处于某个较低层级时，要认识到该代码是危险的，是一个可能发生不可恢复错误、导致系统挂起的区域。该代码需要额外关注，以确定是否可能出现任何问题（并希望防止它）。

通常，在电路板启动期间或使用调试器时，你不希望看门狗处于活动状态。否则，系统会在断点后复位。有一个简单直接的方法来关闭看门狗将有助于调试。如果你有日志记录方法，请确保在启动时如果看门狗已开启则打印一条消息。这是你不想在生产测试时忘记启用的那些事情之一。或者，你可以在看门狗被服务时翻转一个 LED，给系统一个从外部容易看到的心跳，让用户知道一切都在按预期工作。

看门狗术语

服务看门狗使其不触发复位，传统上被称为"踢狗"（kicking the dog）。

当我在一家对宠物友好的小公司工作时，这引起了恐慌。在午餐时间看狗玩耍很棒，而且有点令人平静。然而，有一天当我们为一个重要客户准备审查我们的代码时，我们的 CEO 看到主循环中的 KickTheDog() 函数后大发雷霆。他坚决地解释说，在我们公司，任何狗——无论真实的还是虚拟的——都不会被踢。永远不。

我们将函数名重构为 PetTheDog()。在重要会议那天，当客户看到我们这个政治正确的安全网时，他们窃笑起来。我不确定术语是什么时候改变的，但在那之后的几年里，我看到越来越少的踢狗，更多的是抚摸、喂食或遛狗。你选择怎么做取决于你，但你永远不会真的踢狗，对吧？

这里有三个要点：(1) 标准事物的术语会改变，(2) 语言很重要，(3) 永远不要让你的 CEO 看到你的代码。

主循环

本章以一些关于 RTOS 术语的重要说明开始（尽管我不是假设你的系统上有 RTOS，但这些概念可以迁移到裸机）。然后介绍了很多构建状态机的方法。这些都很好，但我们如何真正开始呢？

我们通常从主循环开始。和状态机一样，有很多种设置主循环的方法。它们各有利弊，所以你需要找出最适合你的方式。

轮询与等待

我喜欢 Arduino 简单明了的程序结构：

setup: init loop:

toggle LED

delay

在幕后，Arduino 开发环境放置了一个 main 函数，该函数调用 setup 函数进行初始化。隐藏的 main 函数会做它需要的其他电路板和处理器初始化。一旦你的 setup 和隐藏的初始化完成，它就启动一个永久循环，在每次循环中调用你的 loop 函数（但也可能根据需要调用它自己的设置函数）。图 6-5 显示了系统各部分如何交互。开发环境隐藏了细节，但在某处，有一个 main 函数。

我们不需要别人为我们做这件事；我们可以自己编写 main：

main: init while (1)

toggle LED

delay

这就是主循环生命开始的方式，作为一些简单的东西。当然，这个闪烁的灯非常无聊，所以我需要添加一些内容：

main: init while (1)

read inputs

write outputs

toggle LED

delay

注意，"read inputs" 和 "write outputs" 在你代码中可能是其他东西：一个检查命令处理接口的函数；你根据当前时间或被轮询的按钮更新状态机的地方；或者代码将你拥有的输入转换为所需输出的地方。关于这个循环中事情如何发生的顺序，参见图 6-6。

在这个循环中，一切都按预期发生，但有一个大问题：它是阻塞的。如果输入在系统执行延时期间到来，它们不会被处理，直到循环的下一次遍历。如果输入需要快速处理，这可能行不通。

main: init while (1)

write outputs

中断做所有事情

但如果它们不能呢？如果有时输入需要立即运行，不能等待输出完成它的事情怎么办？

假设有一种方法可以在输入数据可用时设置中断，我们可以让中断处理复制数据。这可能是一个发送中断以开始发送数据的传感器，或者是一个允许你在其缓冲区半满时设置中断的通信路径。在输出方面，也许有一个需要时间但会中断告诉你何时准备好下一条消息的通信路径。那么，如果中断做所有工作呢？

timer interrupt: toggle LED

data available interrupt: copy data in

output ready interrupt: copy data out

main: init

set up interrupts

while (1)

pet watchdog

sleep

这里有很多优点。子系统的解耦是好的，因为它导致了关注点分离，每个中断做自己的事情，不依赖其他中断。此外，由于中断指示事情何时发生，主循环可以进入睡眠状态，直到被中断唤醒。这种行为对功耗非常有利（更多关于这方面的内容在第 13 章）。

正如顺序图（图 6-8）所示，这些代码片段中的每一个都是异步的，随时发生，互不依赖。嗯，基本上互不依赖。如果一个中断唤醒了处理器，ISR 运行，然后返回到主循环中 sleep 调用之后。在我的例子中，它抚摸看门狗然后回到睡眠状态。异步方法的缺点是理解执行流程要困难得多（这使得调试困难得多）。

图 6-8. 中断做所有工作的主循环

由于中断在需要时发生，它们的响应时间（系统延迟）应该很快，只要另一个中断没有阻止它们运行。如果中断花费太长时间，优先级和中断丢失可能会成为问题。

当然，中断应该是短的。复制大量数据通常不是一个短的过程；事实上，这是我们要避免在中断服务例程中做的事情。

中断产生事件

相反，我们可以设置一个变量来告诉 main 要做什么，保持我们的中断简短，允许处理器睡眠，并保持系统响应当前需求：

timer interrupt: set global led_change variable

data available interrupt: set global data_available

output ready interrupt: set global output_ready

main: init while (1)

if led_change: toggle led; led_change = false

if data_available: copy input; data_available = false

if output_ready: copy output; output_ready = false

pet watchdog

sleep

这给代码添加了一堆全局变量，通常是制造意大利面条式代码的好方法。然而，事件的顺序不那么不确定了，因为我们可以使用全局变量来控制顺序（只在 data_available 之后运行 output_ready）。中断仍然是异步的，但由于逻辑在正常执行中，我们可以添加一些日志调用，这将使调试容易得多。

另外，处理器仍然可以睡眠，因为中断会唤醒它。

伪代码中没有显示的是我之前在书中已经提到的两个重要点。首先，全局变量是 volatile 的，所以它们不会被编译器的优化器移除（因为根据编译器对主循环的看法，事件变量从未改变）。其次，全局变量只在禁用中断的情况下修改，以防止竞态条件。

如果你的代码及其所有 if 语句看起来像一个状态机，那么，感谢你的关注。

非常小型调度器

第 5 章的非常小型调度器呢？它在这种形式下是什么样子的？如上所述，它遍历任务列表，当某个任务应该运行时调用其关联的回调函数。它完全基于时间：

system tick interrupt: increment current time

main: init while (1)

for each task

if time to run task

call task callback function

set new time to run task

pet watchdog

使用这种方法，每个任务运行到完成。它是一个函数调用，所以可能被像系统定时器滴答（即 systick）这样的中断所打断，但不会被任何其他任务打断。它会在下一个任务可以运行之前完成。这也意味着如果它花费很长时间，排在其后调度的函数可能会被延迟，并且所有任务可能在看门狗被抚摸之前连续运行。虽然所有任务在调度器的一次迭代中都运行是罕见的，但你必须配置看门狗定时器具有足够长的超时时间来允许这种可能性。

如果这对你来说完全正常，我同意；但 RTOS 可以是抢占式的，这意味着更重要的任务可以打断不太重要的任务来使用处理器。RTOS 的调度器通常会在任何 RTOS 相关函数被调用时寻找这样的机会。

但小型调度器运行在 main 中，不做任何花哨的事情。当任务完成时，它从其函数返回。然后处理器可以做其他事情，比如继续执行下一个准备运行的任务。

处理器也可以睡眠，只要它能在下一个任务准备运行时调度一个唤醒中断。大多数定时器允许这种事情，但不是全部。如果不允许，系统将不得不在每个新的 systick 中断时唤醒。

图 6-10 中的顺序图展示了这一点。注意任务之间是异步的（它们不需要按图中显示的顺序执行）。相反，每个任务取决于它需要运行的频率。

图 6-10. 非常小型调度器驱动所有任务，在给定时间运行它们

并非所有东西都必须通过调度器；你可以有其他中断。例如，数据可用中断可以改变任务列表，使输入回调立即发生（嗯，在调度器下一次检查该任务是否准备运行时）。

此外，LED 仍然可以由一个单独的定时器中断来翻转。对于这些主循环风格没有任何硬性规定；混合使用是允许的。

活动对象

还有一种主循环风格我想分享。如果你将非常小型调度器的同步（非中断式）简单性与所有事情在中断中完成时的美好关注点分离结合起来，你就得到了活动对象。这种方法需要一个 RTOS 才能有效，因为它需要真正独立的任务。然而，我在使用蓝牙或状态机的供应商演示代码中经常在嵌入式系统中看到它。这是框架代码，你需要将你的函数和任务添加到现有系统中。

目标是尽可能少地花时间在中断中，让一切都完全异步，并使每个代码片段尽可能分离。这样，你的代码就不会干扰你正在集成的任何系统。

活动对象的一个关键特征是控制反转。不是你的代码控制系统，而是框架负责控制，并在需要你时调用你：

timer interrupt: send event to timer task

timer task: while (1)

wait for event message

if message is toggle LED, toggle LED

data available interrupt: send event to data task

data task: while (1)

wait for event message

if message is data available,

handle data

send output ready to output task

output task: while (1)

wait for message

if message is output ready,

output data

main: init while (1)

pet watchdog

sleep

虽然表面上更复杂，但每个任务完全专注于它所做的事情。每个任务将其数据保持私有：任务只通过异步填充的消息队列进行通信。它们努力保持彼此自治。我最初几次看到活动对象时，感觉有很多重复，必须深入挖掘供应商代码来追踪事件消息如何通过多个任务被正确的任务处理。然而，从供应商的角度来看，事件是一种契约，告诉你正在发生什么，而无需了解你代码的任何信息。

控制反转通常被称为好莱坞原则：

不要打电话给我们，我们会打给你。

识别活动对象的一个好方法是看任务是否围绕消息泵（message pump）组织。通常这由一个等待消息的区域后跟一个大的 switch 语句来实现，该语句依赖于接收到的消息事件。一旦事件处理完毕，任务就回到等待状态。任务不应做任何阻塞调用，它等待的唯一地方就是那一个位置（等待消息）。（并非所有代码都遵循这个规则，有些系统允许延时或其他 RTOS 调用来放弃控制。但让消息泵成为唯一的阻塞点是良好的实践。）

图 6-11 显示了系统各组件之间是如何分离的，最小化了依赖，只允许任务之间使用特定的通信方法。

图 6-11. 活动对象作为操作系统中的真正任务运行，使用消息泵来分离任务之间的依赖

活动对象的另一个名称是 Actor 设计模式。这些活动对象通常实现为事件驱动的状态机。如果你还记得第4章中的依赖注入，它与控制反转有很多相同的理念。我想说术语并不重要，原则才是关键，但行话确实让讨论这些原则变得更容易。

你可能会觉得这些技术术语令人望而生畏，没那么重要，但你永远不知道什么时候会发现自己置身于《星际迷航》的一集里，企业号必须靠精心设计的活动对象来拯救。

延伸阅读 在没有操作系统的情况下运行嵌入式系统（在裸机上运行），并不意味着你可以对操作系统的原理一无所知。恰恰相反，因为你要亲自完成这些工作，你需要更多地了解操作系统是如何运作的，才能重建你所需要的部分。市面上有很多优秀的操作系统书籍，但我最喜欢的是 Andrew Tannenbaum 的经典教材《操作系统：设计与实现》（Pearson 出版）。免费资源方面，可以查看 OSDev Wiki。

我还建议找一本关于小型处理器编程的老书，最好是1980年或之前出版的。例如，我有一本 Rodnay Zaks 的《6502编程》第三版（Sybex 出版）。你可以在图书馆或二手书店找到这类书籍。这种书去掉了围绕处理器的现代浮华（那些让处理器更易用的浮华），让你深入了解处理器在更简单时代是如何工作的。而且，这些书读起来相当有趣，因为它们的预设知识与当前的用户手册大相径庭（我的那本开头有一个叫"什么是编程？"的章节）。

嵌入式软件工程师有时会更关注我们需要学习的硬件细节或与设备应用相关的算法。好的软件技术并不新鲜。关于良好软件实践的最佳入门之一，是1988年的一篇论文："Designing Reusable Classes"（设计可重用类），作者是 Ralph Johnson 和 Brian Foote。如果你想看看，这篇论文在网上可以免费获取。

Quantum Leaps 的 Miro Samek 是活动对象模式和嵌入式系统中良好软件实践的热情倡导者（参见 Quantum Leaps 网站的"资源"部分）。他的书籍和博客文章充满了优秀的信息，但他的 YouTube 视频特别有教育意义，因为他会一边讲解一边编写系统代码。

面试题：十字路口的红绿灯控制

一个小城市认为其十字路口太繁忙，仅靠停车标志不够，需要升级为信号灯。城市管理者请你为信号灯编写代码。共有四组灯，每组有红、黄、绿三个灯泡。还有四个车辆传感器，可以检测车辆是否停在灯前。你从哪里开始？请告诉我你的设计方案，然后写一些伪代码。（在此期间，我会画一个类似图6-12所示的十字路口。如果可以的话，我倾向于在面试者的纸上画这个十字路口。）

图6-12. 小城市的十字路口

这是一个让面试者主导互动的题目。如果他们想讨论设计模式，有很多可谈的。如果他们想跳过设计，直接讨论定时器或传感器硬件，那也行。

| 第6章：管理活动流程

面试者应澄清不明确的问题。在这个问题中，他们应该询问是否有左转灯（没有，这个路口很小，城市目前还不需要这个）。有些人还会问人行横道（也不在初始开发中处理）。

非常优秀的面试者会注意到这个问题只是表面看起来的一半。目标不是控制四组红绿灯，因为两组灯始终是同步的。

和我的所有面试题一样，命名非常重要。我在他们的纸上画图的目的是鼓励面试者在图上添加自己的信息。好的命名方式包括用罗盘方向来标识路口（南北向和东西向），以及一些有意义的称呼（比如"第一大道与主街"）或页面位置（左/右和上/下）。在给图中的元素命名之前，任何伪代码都将毫无意义。

当他们开始深入问题时，我喜欢听他们讲状态机（或自动机、流程图）。我想看到图表或流程图。有些人卡在初始状态上，因为我们都倾向于从"先发生什么"开始。然而，在这个问题中，初始状态相对无趣（不过，如果被问及，我会建议他们从全红灯状态开始）。

在他们梳理了基本内容后，我通常会加一些难题（虽然优秀的面试者往往在我提问之前就已经处理好了）。

第一，如果传感器坏了怎么办？或者城市想要对自行车友好（自行车不会触发汽车传感器）怎么办？这就在状态机中增加了一个定时器，确保路口不会永远困在某个状态中。

第二，这个路口闯黄灯的事故越来越多。他们能做些什么来提升系统的安全性吗？（提示：增加一个短暂的全红灯状态，让车辆在下一个绿灯亮起之前清空路口。）

因为这道面试题本质上是一个逻辑题，我经常对其他工程师突击提问，特别是质量部门的人（"你会如何为这个控制器编写测试方案？"）。
