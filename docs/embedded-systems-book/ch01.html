第1章 引言

Making Embedded Systems — Elecia White 著 | AI 辅助翻译

对于不同的人来说，嵌入式系统意味着不同的东西。对于一直在做服务器开发的人来说，为手机开发的应用程序就是一个嵌入式系统。对于为小型8位微处理器编写过代码的人来说，任何带有操作系统的设备似乎都不那么"嵌入式"。我倾向于告诉非技术人员，嵌入式系统是像微波炉和汽车这样运行软件但又不是计算机的东西（大多数人认为计算机是一种通用设备）。

也许一个无需在技术上争论就能定义这个术语的方式是：嵌入式系统是一种为特定应用而专门构建的计算机化系统。

由于嵌入式系统的使命比通用计算机更加专注，因此它对与完成手头任务无关的事情支持较少。硬件通常存在各种约束：以较低速度运行以节省电池电量的 CPU、使用更少内存以便以更低成本制造的系统、只有特定速度或仅支持部分外设子集的处理器。

硬件并非系统中唯一受到约束的部分。在某些系统中，软件必须具有确定性（每次完全相同）或实时性（始终足够快地响应事件）。有些系统要求软件具有容错能力，在面对错误时能够优雅降级。例如，维修有故障的软件或损坏的硬件可能不可行的系统（如卫星或鲸鱼身上的追踪标签）。其他系统则要求软件在出现问题的第一个迹象时就停止运行（例如心脏监护仪不应该静默地发生故障）。

这个简短的章节将介绍嵌入式系统的高层次概览。实际上，你完全可以去读维基百科的文章，但这是让我们互相了解的一种方式。遗憾的是，本章主要讨论的是嵌入式系统开发有多么困难。

在不同编译器、调试器和资源约束之间，我们设计和实现代码的方式与其他类型的软件不同。有些人可能会说这个领域有点落后，但这并不正确；在大多数情况下，我们只是专注于解决不同的问题。不过，确实有一些有用的软件工程技术被忽视了（但这正是本书其余部分要讨论的内容）。

嵌入式系统最棒的事情之一就是创客运动。人人都喜欢发光的灯，因此人们对从事底层软件开发的职业产生了兴趣。如果你就是其中之一，欢迎你。但我承认，我预期本书的读者是那些有硬件或软件经验、需要知道如何把中间的那部分做好、做高效的人。

在每章的末尾，我都会放一个与本章内容略显相关的面试题。我职业生涯中的成长活动之一就是学习如何面试团队职位的候选人。由于找不到关于如何做这件事的资源，我深感失望，所以我把自己最喜欢的面试题以及作为面试官我所关注的东西放了进来。这些问题有点奇怪，但我希望你跟我一样喜欢它们。

坦率地说，我希望你跟我一样享受嵌入式系统开发的所有方面。挑战是存在的，但那正是有趣的部分。

嵌入式系统开发

嵌入式系统很特别，给开发者带来了独特的挑战。大多数嵌入式软件工程师都会开发一套工具包来应对这些约束。在我们开始构建你的工具包之前，让我们先看看与开发嵌入式系统相关的困难。一旦你熟悉了你的嵌入式系统可能受到哪些限制，我们将开始介绍一些指导我们找到更好解决方案的原则。

编译器与语言

嵌入式系统使用交叉编译器。虽然交叉编译器在你的台式机或笔记本电脑上运行，但它生成的代码却不能在那里运行。交叉编译生成的镜像在你的目标嵌入式系统上运行。因为代码需要在你的嵌入式处理器上运行，目标系统的供应商通常会出售交叉编译器，或提供一份可用的交叉编译器列表供选择。许多大型处理器使用 GNU 工具家族中的交叉编译器，例如 GCC。

嵌入式软件编译器通常只支持 C 语言，或者支持 C 和 C++。此外，一些嵌入式 C++ 编译器只实现了该语言的一个子集（多重继承、异常和模板通常缺失）。其他语言也越来越受欢迎，但 C 和 C++ 仍然是最主流的。

无论你的软件需要使用哪种语言，你都可以实践面向对象设计。封装、模块化和数据抽象这些设计原则几乎可以应用于任何语言中的任何应用。目标是使设计健壮、可维护且灵活。我们应该尽可能从面向对象阵营中获取帮助。

从整体来看，一个嵌入式系统可以被视为等同于一个对象，特别是在它工作于一个更大系统中的时候（例如遥控器与智能电视通信、工厂中的分布式控制系统，或者汽车中的安全气囊展开传感器）。在更高的层次上，一切本质上都是面向对象的，将这一点延伸到嵌入式软件中是合乎逻辑的。

另一方面，我不建议严格遵循所有面向对象设计原则。嵌入式系统受到太多方向的拉扯，无法确立这样的戒律。一旦你认识到各种权衡，你就可以在软件设计目标和系统设计目标之间取得平衡。

本书中的大多数示例使用 C 或 C++。我认为语言不如概念重要，所以即使你不熟悉语法，也请看一看代码。本书不会教你任何编程语言（除了一些汇编语言），但好的设计原则是超越语言的。

调试

如果你要调试运行在计算机上的软件，你可以在该计算机上编译和调试。系统会有足够的资源来同时运行程序和支持调试。事实上，硬件甚至不知道你在调试应用程序，因为这一切都是在软件层面完成的。

嵌入式系统则不是这样。除了交叉编译器，你还需要一个交叉调试器。调试器位于你的计算机上，通过一个特殊的处理器接口与目标处理器通信（见图 1-1）。该接口专门用于让其他人在处理器工作时"窃听"其运行。这个接口通常被称为 JTAG（发音为"jay-tag"），无论它是否真正实现了那个广泛使用的标准。

处理器必须消耗一些资源来支持调试接口，允许调试器在运行时暂停处理器，并提供常规的调试信息。支持调试操作会增加处理器的成本。为了降低成本，一些处理器只支持有限的功能子集。例如，添加一个断点会导致处理器修改已加载到内存中的代码，使其指示"停在这里"。然而，如果你的代码在闪存（或任何其他类型的只读存储器）中执行，处理器无法修改代码，而必须设置一个内部寄存器（硬件断点），并在每个执行周期将其与正在运行的代码地址进行比较，匹配时停止。这可能会改变代码的时序，导致那些只在调试时（或恰好不在调试时）才会出现的恼人 bug。内部寄存器也会占用资源，因此通常只有有限数量的硬件断点可用（通常只有两个）。

总而言之，处理器支持调试，但如果你来自非嵌入式软件领域，其调试支持可能不如你习惯的那么充分。

在你的 PC 和嵌入式处理器之间通信的设备通常被称为硬件调试器、编程器、调试探针、在线仿真器（ICE）或 JTAG 适配器。这些术语可能（在某些程度上不太准确地）指代同一个东西，也可能是多个不同的设备。调试器是特定于处理器（或处理器系列）的，所以你不能把一个项目上用的调试器拿来假设它能在另一个项目上工作。调试器的成本会累积起来，特别是当你收集了足够多的调试器，或者有一个大型团队在为你的系统工作时。

为了避免购买调试器或应对处理器的限制，许多嵌入式系统被设计为主要通过 printf 或某种轻量级日志记录到一个未使用的通信端口来进行调试。尽管这极其有用，但它也可能改变系统的时序，可能导致一些 bug 只在调试输出关闭后才暴露出来。

为嵌入式系统编写软件可能会很棘手，因为你必须在系统需求和硬件约束之间取得平衡。现在你需要在待办事项列表中再增加一项：让软件在某种程度上具有敌意的环境中可调试，这一点我们将在第 2 章中进一步讨论。

资源约束

嵌入式系统被设计用来执行特定任务，因此会去除完成其使命不需要的那些资源。需要考虑的资源包括：

  • 内存（随机存取存储器）
  • 代码空间（只读存储器或闪存）
  • 处理器周期或速度
  • 功耗（这转化为电池寿命）
  • 处理器外设

在某种程度上，这些资源是可以互换的。例如，你可以用代码空间换取处理器周期，将代码的某些部分写得占用更多空间但运行更快。或者你可以降低处理器速度以减少功耗。如果你没有某个特定的外设接口，你也许可以用 I/O 线和处理器周期在软件中创建它。然而，即使可以进行权衡，每种资源的供应也是有限的。资源约束的挑战是嵌入式系统最紧迫的问题之一。

另一组挑战来自与硬件的交互。交叉调试带来的额外负担可能令人沮丧。在电路板启动期间，不确定 bug 出在硬件还是软件中可能会使问题难以解决。与你的计算机不同，你编写的软件可能会对硬件造成实际损害。最重要的是，你必须了解硬件及其能力。这些知识可能不适用于你下一个要开发的系统。你需要快速学习。

一旦开发和测试完成，系统就会进入制造阶段，这是大多数纯软件工程师永远不需要考虑的事情。然而，创建一个能够以合理成本制造的系统，是嵌入式软件工程师和硬件工程师都必须牢记的目标。支持制造是确保你创建的系统能够被高保真地复制的一种方式。

制造完成后，设备会进入现场。对于消费类产品来说，这意味着它们进入数百万家庭，你创造的任何 bug 都会被很多人"享用"。对于医疗、航空或其他关键产品，你的 bug 可能是灾难性的（这就是为什么你需要做如此多的文书工作）。对于科学或监测设备，"现场"可能是一个设备永远无法被回收的地方（或者只能冒着巨大风险和费用才能回收；想想火山口里的设备），所以它必须好用。你的系统在离开你之后将要经历的生活，是你在设计软件时必须考虑的事情。

在你弄清楚了所有这些问题并为你的系统确定了应对策略之后，还有一个最大的挑战，一个所有工程分支都共有的挑战：变化。不仅产品目标会改变，项目的需求在其整个生命周期中也会发生变化。在开始阶段，也许你只是想拼凑出一些东西来试试看。随着你变得更认真、更好地理解（并定义）产品目标和你正在使用的硬件，你会开始构建更多的基础设施，使软件变得可调试、健壮和灵活。在资源受限的环境中，你需要决定在开发时间、RAM、代码空间和处理器周期方面你能负担多少基础设施。你最初开始构建的东西不会是你开发完成时最终得到的东西。而开发几乎永远不会真正完成。

创建一个为应用专门构建的系统有一个不幸的副作用：当应用形态发生变化时，系统可能无法支持变化。嵌入式系统工程不仅仅是关于严格的约束和系统的最终归宿。目标是弄清楚这些约束中哪些会在产品开发的后期成为问题。你需要预测可能的变化路径，并尝试设计出足够灵活的软件，以适应应用无论走哪条路。拿出你的水晶球吧。

应对这些挑战的原则

嵌入式系统可能看起来像一个拼图，各个拼块相互咬合（而且只有一种拼法）。有时你可以强行将拼块拼在一起，但最终得到的画面可能与盒子上的图案不同。然而，我们应该抛弃"最终结果就是在项目结束时交付的单一代码版本"这种想法。

相反，想象这个拼图有一个时间维度，贯穿其整个生命周期：构思、原型制作、电路板启动、调试、测试、发布、维护，然后周而复始。灵活性不仅关乎代码现在能做什么，还关乎代码如何应对其整个生命周期。我们的目标是在应对嵌入式系统固有的资源约束和其他问题的同时，保持足够的灵活性以满足产品目标。

我们可以从软件设计中借鉴一些优秀的原则，使系统更加灵活。利用模块化，我们将功能分离为子系统，并将每个子系统使用的数据隐藏起来。通过封装，我们在子系统之间创建接口，使它们彼此了解不多。一旦我们有了松耦合的子系统（如果你喜欢的话，也可以叫它们对象），我们就可以修改软件的一个区域，而确信它不会影响另一个区域。这让我们能够在需要时将系统拆开并以略有不同的方式重新组合。

识别在何处将系统分解为多个部分需要练习。一个好的经验法则是考虑哪些部分可以独立变化。在嵌入式系统中，这得益于你可以考虑的物理对象的存在。如果传感器 X 通过通信通道 Y 进行通信，那么这些是独立的事物，是成为独立子系统（和代码模块）的良好候选者。

如果我们将事物分解为对象，就可以对它们进行一些测试。在一些项目中，我有幸拥有优秀的 QA 团队。在另一些项目中，我的代码和使用系统的人之间没有任何人把关。我发现，在软件发布之前捕获的 bug 就像礼物一样。错误在流程中越早被捕获，修复成本就越低，对每个人来说就越好。

你不必等待别人给你送礼物。测试和质量是相辅相成的。当你在思考如何编写一段代码时，花一些时间考虑你将如何测试它。为你的系统编写测试代码会使其变得更好，为你的代码提供一些文档，并让其他人觉得你写出了优秀的软件。

为代码编写文档是减少 bug 的另一种方式。在对代码进行注释时，知道到什么层次为止可能很难：

i++; // increment the index

不，不是那样的。像这样的代码行很少需要注释。目标是为你自己那样的人写注释，那个在一年后回头看这段代码的人。到那时候，未来的你可能正在做不同的事情，并且已经忘记了过去的你想出了什么创造性的解决方案。未来的你可能甚至不记得写过这段代码，所以用一点定位提示来帮助自己吧。不过总的来说，假设读者拥有和你一样的头脑和一般背景，所以文档应记录代码做了什么，而不是它是如何做的。

最后，对于资源受限的系统，总有一种尽早且频繁优化代码的诱惑。抵制这种冲动。先实现功能，让它们工作起来，测试它们，然后在需要的时候再让它们变得更小或更快。

你只有有限的时间：在有了一个可工作的子系统之后，通过寻找更大的资源消耗者，把精力集中在能获得更好结果的地方。优化一个很少运行的函数对你没有任何好处，如果它的运行时间被另一个频繁运行的函数所掩盖的话。可以肯定的是，应对系统的约束确实需要一些优化。只是在开始调优之前，要确保你了解资源被用在何处。

我们应该忘掉小的效率，大约 97% 的情况下：过早优化是万恶之源。
——Donald Knuth

原型与创客开发板

"但是等等，"你说，"我已经用 Arduino 或 Raspberry Pi Pico 搭建了一个可以工作的系统。我只需要弄清楚如何把它变成产品就行了。"

我明白。系统几乎做到了你想要的一切。项目看起来几乎完成了。现成的开发板非常棒，尤其是那些对创客友好的。它们让原型制作变得更容易。然而，原型不是产品。

在这个阶段，有许多经常被遗忘的任务。固件将如何更新？系统是否需要休眠以降低功耗？在发生灾难性错误时我们是否需要看门狗？我们需要为未来的 bug 修复和改进保留多少空间和多少个处理周期？我们如何制造许多设备而不是一个手工制作的单元？我们将如何测试安全性？无法解释的用户指令？极端情况？损坏的硬件？

抛开软件不谈，当现有的现成开发板不能满足你的需求时，通常就需要定制电路板。开发板可能太脆弱了，靠脆弱的导线连接。它们可能对你的目标市场来说太贵，或者功耗太大。它们的尺寸或形状可能不合适。它们可能无法承受预期的环境条件（如汽车内的温度波动、受潮或进入太空）。

无论出于什么原因需要定制电路板，这通常意味着要移除作为处理器开发板一部分的编程（和调试）硬件。定制硬件还会让你脱离一些简化的开发环境和软件框架。使用微处理器供应商的硬件抽象层配合传统编译器，你可以获得更小的代码体积（通常也更快）。在你和处理器之间没有任何中间层，这让你能够实现确定性和实时性处理。你也许还能够使用和配置一个实时操作系统（RTOS）。你可以更容易地理解你在库中使用的代码的许可协议。

添加外部编程器/调试器可以让你拥有超越 printf 的调试能力，让你看到代码内部的情况。在经历了漫长而艰难的调试方式之后，这感觉相当神奇。

尽管如此，在原型和发货设备之间、在支持桌面上的一台设备和现场的一千台或一百万台设备之间，存在着巨大的鸿沟。不要因为所有功能终于工作了一次（在完美条件下）就误以为项目已经完成了。

开发板和简化的开发环境非常适用于原型制作和帮助选择处理器。但总有一天，设备需要变得更小、更快和/或更便宜。到那时，资源约束就会显现出来，你需要像本书这样的资源来帮助你。

  • Design Patterns: Elements of Reusable Object-Oriented Software，作者 Erich Gamma 等（Addison-Wesley 出版）。这本书最初于 1995 年出版，引发了软件设计模式革命。由于其四位合作者，它通常被称为"四人帮"（Gang of Four）之书（标准设计模式也可能被称为 GoF 模式）。
  • Head First Design Patterns，作者 Eric T. Freeman 等（O'Reilly 出版）。这本书比 GoF 原作要易读得多。具体的示例让我更容易记住。

关于从原型到发货的更多信息，我推荐 Alan Cohen 的 Prototype to Product: A Practical Guide for Getting to Market（O'Reilly 出版）。

面试题：Hello World

这里有一台计算机，配有编译器和编辑器。请实现"hello world"。在你完成基本版本之后，添加从命令行获取名字的功能。最后，告诉我你的代码执行之前发生了什么——换句话说，在 main() 函数之前发生了什么。（感谢 Phillip King 提供此题。）

在许多嵌入式系统项目中，你必须从头开始开发一个系统。通过这道题的第一部分，我寻找的是一个能够从空白开始填写基本功能的候选人，即使是在不熟悉的环境中。我希望他们对编程有足够的熟练度，使这道题对他们来说是直截了当的。

这是一道扎实的编程题，所以你最好熟悉你简历上列出的语言。任何一种都可以用于这道题。当我要求实现一个"hello world"时，我寻找的是语言的细节（这意味着知道在 C 和 C++ 中要包含哪个头文件以及使用命令行参数）。我希望面试者有能力根据编译器错误找到并修复语法错误（不过，当他们能毫无错误地输入整个程序甚至没有拼写错误时，我会格外印象深刻）。

就我个人而言，我打字还不错，但如果有人在我肩膀后面看着，我每打一个字母都会出错。这没关系，很多人都是这样。所以不要让这影响你的表现。只需专注于键盘和代码，而不是你的打字技巧。

问题的后半部分才是我们开始进入嵌入式系统的地方。纯粹的计算机科学家倾向于将计算机视为一个执行他们优美算法的理想化想象盒子。当被问及 main 函数之前发生了什么时，他们往往会回答"你知道，程序就运行了"，但不理解这意味着什么。

然而，如果他们提到"start"或"cstart"，那在面试中就已经走在了正确的道路上。总的来说，我希望他们知道程序需要初始化，这超出了我们在源代码中看到的内容，无论是什么平台。我喜欢听到他们提到设置异常向量以处理中断、初始化关键外设、初始化堆栈、初始化变量，以及如果有 C++ 对象的话，调用它们的构造函数。如果他们能描述什么是隐式发生的（由编译器完成）和什么是显式发生的（在初始化代码中），那就更好了。

最好的答案是逐步描述可能发生的所有事情，并解释为什么这些步骤很重要，以及它们在嵌入式系统中是如何发生的。经验丰富的嵌入式工程师通常从向量表开始，从复位向量出发，然后转向系统的上电行为。这些内容将在本书后面介绍，所以如果这些术语对你来说是新的，不用担心。

提出这道题的电气工程师（EE）会给予额外加分，如果在进一步讨论上电行为时，候选人能解释为什么嵌入式系统不能在开关被拨动后 1 微秒内启动并运行。EE 希望听到对上电时序、电源爬升时间、时钟稳定时间和处理器复位/初始化延迟的理解。
