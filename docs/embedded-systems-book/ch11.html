第11章 用更少做更多

Making Embedded Systems — Elecia White 著 | AI 辅助翻译

以更少的资源做更多的事

工程需要技术技能和对相关技术的深刻理解。编写优秀的嵌入式软件则更进一步，还需要一个狡猾的头脑和对解谜的亲和力。 在一个拥有所需一切资源的系统上实现需求，就像转动隐喻中的曲柄来得到答案。有些解决方案比其他的更优雅，但大多数都能足够好地工作，让产品得以出货。当你面对一个似乎不可能容纳你所需一切的系统时，事情就变得更有趣了。你可以在功能上妥协，但那样做还有什么乐趣呢？ 对我来说，嵌入式系统实现的精彩之处在于那种兴奋感：找到恰到好处的调整就能释放出几个处理器周期，为释放八个字节的RAM而激动不已，深入挖掘映射文件找到一整段可以回收供自己代码使用的区域，以及意识到只要能挤出几毫秒的深度睡眠时间，你的产品就能获得那梦寐以求的绿色奖项。 这一切的缺点是，你很可能会使系统变得更加脆弱。例如，当你通过让两个原本解耦的子系统共享RAM来释放内存时，这些子系统就变得耦合在一起了。系统的维护者会对这些隐藏的耦合感到困惑和沮丧。代码不再模块化，子系统也无法复用。灵活性丧失了。 本章探讨如何从你的系统中获得更多。我们需要首先分析我们拥有的资源和需要的资源。有些资源优化技术允许你用一种资源换取另一种资源。识别哪些资源是充裕的，与确定稀缺资源消耗到哪里了几乎同等重要。 最重要的资源之一是开发工作量。你的时间非常宝贵。你需要权衡一个解决方案的价值与实现它所需的时间。 例如，换用同一系列中更大、更快的芯片会对所有产品产生成本，如果你只生产少量产品，这可能是划算的；用内存换取处理器周期可能需要你重构一些代码；而逐行优化汇编代码则需要巨大的工作量（和技能）。

需要更多代码空间

在一个没有足够代码空间的系统上实现应用，就像试图在一本太小的册子里写学期论文。即使你提前规划并试图确定每个要点应分配多少空间，最终你还是得在最后一页用极小的字迹书写，甚至把边距都用上。本节将帮助你应对代码空间紧张的情况。

阅读映射文件（第一部分）

当链接器在构建过程中报错时，我会感到一种不祥的预感。编译器会提供各种友好的建议并批评我的打字错误，但链接器通常只在有重要事情时才发声。 另一方面，如果你知道该看哪里，链接器会提供丰富的信息。"链接器脚本入门"描述了链接器的输入。输出的映射文件更容易阅读，尽管对大多数开发者来说仍然很陌生。 你可能需要配置链接器来输出映射文件。在可执行文件所在的目录中查找.map文件。如果没有找到，请查看编译器或链接器手册。 映射文件是工具链相关的。本节的例子来自基于GNU的工具链，面向NXP LPC13xx。大多数映射文件包含相同的信息，只是顺序可能不同或格式各异。你需要根据自己的映射文件做出一些合理的推测。如果你不确定映射文件是否给出了你要找的信息，可以试试这个方法：先做一份副本，修改代码，重新构建，然后将生成的映射文件与原始映射文件进行diff比较。 用于LPC13xx的GNU链接器以一个列表开头，列出了包含的库模块以及哪个模块导致了该库的包含。在这个例子中，libcr_c.a被包含在构建中，因为你的代码模块aes256.c调用了memcpy()。请注意，只有libcr_c.a库的部分内容被包含（具体来说是memcpy.o）： Archive member included because of file (symbol) ../lib/gcc/arm-none-eabi/4.3.3/../../../arm-none-eabi/lib/thumb2/libcr_c.a (memcpy.o)./src/aes256.o (memcpy)

函数并不是唯一占用代码空间的东西。在示例映射文件的后面是只读数据节：

*(.rodata*) .rodata.str1.1 0x000070cc 0x36 ./src/main.o .rodata 0x0000715c 0x10 ./src/aes256.o .rodata.str1.1 0x0000716c 0x35 ./src/aes256.o 这里，main有0x36字节的str1.1，这不是我会给变量起的名字。实际上，这是编译器给字符串变量自动分配的名称。所以无论哪里有常量字符串（如"Hello world"），编译器都会将它们收集到一个区域，放入只读数据节。除了aes256.o中的0x35字节字符串数据外，前面的片段还显示了文件中未指定的数据（长度为0x10）。在源文件的测试函数中，声明了一个带有静态初始化器的变量： uint8_t buf[16] = {0xe5, 0xaa, 0x6d, 0xcb, 0x29, 0xb2, 0x71, 0xae, 0x0e, 0xbc, 0xfa, 0x7a, 0xb2, 0x2b, 0x57, 0x59}; 因为它位于函数内部，其他文件无法通过名称看到它。因此映射文件不显示变量名，但列出了常量，因为它们占用了可执行映像中的空间。 所有常量都占用空间，无论它们是在#define声明中声明的，还是使用关键字const声明的。全局常量通常在映射文件中可见，但用#define声明的常量最终出现在代码中，因此不会以类似的方式被列出。你可以在.rodata下的映射文件中看到使用const声明的变量： .rodata 0x00007ab8 0x6A ./src/displayMap.o kBackgroundInfo 0x00007b8a kBorderInfo 0x00007bf4 可能有一些节标记为fill。这表示文件之间的数据出现了未对齐，通常是因为某个文件使用了一个小于处理器原生格式的常量。例如，一个五字符长的字符串在32位处理器上将消耗1.25个字，导致链接器填充三个字节（通常用零填充）。这是浪费的空间，但很难回收。除非你真的需要每一个字节，否则最好专注于更大的内存用户。 映射文件的其余部分充满了丰富的RAM详细信息（我们稍后会讨论）和调试信息（通常没什么用，尽管你的调试器可能会使用这些信息）。 如果映射文件展示数据的方式对你来说不好用，那就自己写脚本来解析它！读取映射文件，创建一个输出表格，其中单元格的高度与函数的大小成正比。用Python来做这件事相当容易，特别是如果你使用HTML作为输出的话。

排除法

既然你知道了什么在占用代码空间，就可以开始缩减大小了。从你的工具开始。除了通常看到的不同优化级别（用于使代码运行更快，例如-O3编译器选项）之外，还有特殊的优化标志用于使代码更小（例如，在GCC中，-Os尝试优化代码大小而非执行速度）。这可能足以解决你的代码空间问题。 如果你在开启优化后得到了不同的运行时结果，请检查所有变量是否已初始化，以及volatile变量是否被标记为volatile。偶尔编译器会禁止一些罕见但合法的特性，所以如果你排除了明显的问题，请查阅编译器手册。 如果编译器优化还不够，在寻找内存时要保持计分，这样你就能知道哪些更改带来了最好的改进。这不仅让你对各种改进类型有所体会，还能帮助你对同事表达权衡（例如，"是的，那段代码现在更丑了，但它节省了2KB的代码空间"）。 如表11-1所示，创建一个电子表格，从基线数字开始。对每一次更改，填写一行，这样你就能看到各项更改的相对价值。如果你的链接器输出给你的是十六进制数字，你可能想让电子表格将其转换为十进制（或反过来）。

很多时候你可以编写一个函数来替代库。其他时候你需要想办法绕过限制。以下是一些常见的例子来启发思路：

• 用定点表示法替代浮点数（参见第12章）。 • 用几个不接受可变参数的函数替代printf（例如，Log、LogWithNum）。 • 用自己的实现替代strcpy，以排除字符串库。 • 用宏替代abs函数，以消除浮点数数学库的依赖。 请注意，标准库中并没有什么魔法。你的开发环境自带的库可能对你的设备来说不是最高效的。没有任何法律规定你必须使用埋在工具目录中的标准库。如果你去寻找，还有其他选择。 Embedded Artistry有一个专门用于嵌入式系统的C标准库（LibC，在GitHub上可用）。它提供了一套精简的功能，适合资源极其受限的环境。它专为可移植性和快速启动而设计。其文档也非常出色，代码可读性很好。相关的博客文章也很有用。 话虽如此，如果没有必要就不要编写自己的库。标准库和现成的库通常比你自己在有限时间内能写出来的要规范得多、测试也更充分。利用他人投入的时间和精力吧。 函数与宏：哪个更小？ 保持代码的模块化对可读性至关重要。然而，每个函数都有代价，会增加代码空间、RAM和处理器时间。代码空间的代价是容易量化的。 例如，我需要一个求三个变量最小值的算法的小型实现（示例11-1）。

示例11-1. 求三个值最小值的算法

if a < b, if a < c, return a else, return c else, if b < c, return b else, return c 我编写了一些代码来尝试不同的实现方案。首先，我在main函数中直接写出代码并编译，以获得我的代码空间基线（以字节为单位，由于自动编译的其他杂项，这接近3KB）。我将实现改为宏： #define min3(x, y, z) (((x)<(y))?(((x)<(z))?(x):(z)):(((y)<(z))?(y):(z)))

不记得三元条件运算符了吗？它是if语句的简写形式：

test ? value if test is true : value if test is false 这不仅使你的代码更紧凑，有时还能促使编译器生成更优化的代码。 然后我修改代码多次运行该宏，以获取不同的代码空间大小。我把宏改为函数并运行相同的测试。有点奇怪的是：编译后的代码大小是相同的，无论我使用内联函数、普通的局部函数还是外部函数。 inline关键字本应让函数表现得像宏一样，将代码复制到每个调用位置。然而，inline只是对编译器的建议，而非要求。编译器如何接受这个建议是非常特定于编译器的。通常有编译器特定的pragma来禁止内联（例如，GCC中的__attribute__((noinline))）。 在记录大小之后，我开启了优化并重新运行测试，记录每种实现相对于基线的字节差异（见表11-2）。整个过程中我把所有变量都标记为volatile，这样编译器就不会删除看似没有副作用的代码（例如，中间的宏或函数调用）。

常量和字符串

在浏览映射文件时，你可能会发现调试字符串占用了大量的代码空间。这是一个非常棘手的两难困境，因为这些调试字符串提供了宝贵的信息和有用的注释。 如果你已经实现了一个日志API（参见第27页的"创建接口"），你已经具备了在运行时按子系统开关调试的能力。要消除调试字符串，你需要更进一步，在编译时移除这些函数。

你仍然可以使用以下常见惯用法获得一些灵活性（和一些文档），它允许你关闭特定子系统（本例中是电机子系统）的日志：

寄存器和局部变量

与全局变量不同，估算局部变量（函数内部变量）消耗的RAM要困难得多。寄存器是CPU的内存单元。有些处理器不能直接在RAM上执行操作，而是必须将值从RAM加载到寄存器中，在寄存器上执行操作，然后将信息存回RAM。对于一行写着下面这样的代码来说，这需要很多条指令： i++; 并非每个处理器都需要经历这样的辗转，但对任何处理器来说，使用寄存器都更快。局部变量之所以难以在计算RAM使用量时统计，是因为许多局部变量在其整个生命周期中都存在于寄存器中。 C语言有一个名为register的关键字，本意是给编译器一个提示，告诉你认为哪些变量应该放在寄存器中。这个关键字通常被忽略，如果它真的被实现了的话。

函数参数

函数的输入参数通常放在寄存器中，而不是栈（RAM）上。如果你的函数只有少量参数，你可以鼓励编译器这样做。一个好的经验法则是每个函数少于四个参数。如果你有一个32位处理器，那就是四个32位变量，而不是把十几条数据塞进四个结构体中。 事实上，如果你有一个N位处理器，尽量使用N位变量。更大的变量通常不适合放进宝贵的寄存器中。（更小的变量往往会增加处理器步骤，因为编译器只尝试访问你感兴趣的那一部分。） 要使用寄存器，你通常需要按值传递参数。如果你按引用传递（或按指针传递），你发送的是数据的地址。地址可能在寄存器中，但数据需要在RAM中访问。例如： int variable= 10; function(&variable); /* 这比按值传递消耗更多的RAM，

因为variable必须在RAM中才能有地址 */

最小化作用域

你可能熟悉命名空间（即变量根据编程语言规则有效的范围）。一个变量可以是全局的，此时其命名空间作用域是整个程序。也可以声明在文件中、函数中，甚至是函数的指定区域中（例如循环内部）。然而，还有另一种形式的作用域：变量被代码使用的位置。你可能在函数中定义了10个变量，使得它们的命名空间是整个函数，但如果你只在有限的区域内使用每一个变量，那么它的作用域就是那个区域，而不是整个函数。 为了最高效地使用寄存器，每个函数在任何时候都应该只使用少量的变量。当优化开启时，你的编译器会移动代码以限制变量的作用域并释放寄存器。然而，你可以帮助它理解正在发生什么。举个简单（且有些蹩脚）的例子，以下代码片段需要让每个数组元素的值等于它在数组中的位置。它进行一些处理，然后需要将数组重新初始化为其原始值再继续： for (i=0; i < MAX_ARRAY_LENGTH; i++) { array[i] = i; }

… /* 对数组做一些操作，需要再次设置它 */

/* i仍然等于最大数组值，所以减一然后再次运行循环 */

for (i--; i >= 0; i--) { array[i] = i; } 程序员认为避免重新初始化i可以节省几个周期。然而，按照这种写法，i的值必须在其他处理步骤中被记住，即使它实际上并不重要。变量的作用域被无谓地扩大了。我们可以重写代码，使编译器能够在不使用i时将其忘记（编译器可以为另一个变量重用寄存器）： for (i=0; i < MAX_ARRAY_LENGTH; i++) { array[i] = i; } for (i=0; i < MAX_ARRAY_LENGTH; i++) { array[i] = i; } 对于这个例子，解决方案显而易见（而且代码更清晰）。然而，当你审视自己的代码时，你能看到哪些地方可以减少变量的作用域吗？也许可以先完成对一个变量的所有处理，再转向另一个？ 不要担心函数中变量的总数。如果你限制每个变量的作用域，并且在每个作用域内限制活跃变量的总数，编译器就能搞定剩下的工作。重用变量并不总是值得的，特别是当你的编译器无法识别一个在新作用域中使用的旧变量时。

全局变量的利弊：RAM与栈

全局变量名声不好。它们参与了各种意大利面条式代码，不断与莫名其妙的外部力量合谋控制代码流程，而且不知道"可重入"这个词是什么意思。¹ 使用全局变量的程序员常被指责为懒惰。但懒惰和便利并不是使用全局变量的唯一理由。它们确实有好的一面。 不过，先再多说说它们不好的一面。全局变量总是占用RAM。它们几乎总是比局部（寄存器）变量访问更慢。所以如果你有一个可以被局部变量替代的全局变量，就把它变成局部变量。即使它最终落在栈上而不是寄存器中，一旦程序执行超出其作用域，那部分RAM就可以被其他地方自由使用。 那么什么时候全局变量能节省RAM呢？假设你有一个函数调用链，需要在多个函数中使用某个变量（或者更糟的是，你只在函数链的末尾才需要这个数据）。如果你通过参数将数据传递给链中的每个函数，并伴随中间处理，编译器可能无法在整个链中始终将数据保留在寄存器中。因为它是每个函数的参数，数据会被多次放到栈上。全局变量存储在栈之外，可以绕过这个过程。

巧妙的内存叠加

你的系统有几个大缓冲区吗？我在自己的一些系统中发现的一些特别大的缓冲区包括：显示缓冲区、通信缓冲区和传感器输入缓冲区。一旦你识别出系统中的大缓冲区，问问自己它们是否都需要同时使用。 例如，也许你的显示缓冲区是用来构建图像的，然后闲置直到下次需要更新显示时再次构建。或者传感器输入缓冲区在等待感兴趣的事件时并不需要。一旦你注意到事件，就需要整个缓冲区来排队数据，但在那之前，只需要其中一小块区域。又或者，你有一个大的通信缓冲区用于接收要加载的新代码，但通常只需要其中很小一部分。这些听起来熟悉吗？ 如果你的系统使用动态内存分配，这些子系统可能会分配和释放其内存，以避免占用RAM资源。然而，如果你已经禁止了动态内存分配（而且如果使用块分配器又显得小题大做），你的系统可能会 ¹ 如果一个子程序可以在执行中途被中断，然后在其前一次调用完成之前被安全地再次调用，则该子程序是可重入的。（详见第134页"可重入函数"。） 受益于RAM叠加。这是指两个（或更多）子系统共享其部分或全部分配的内存，但每次只有一个可以使用。通过复用资源，你实际上获得了更多的RAM。图11-3展示了一个处理器上可用的4KB RAM缓冲区。没有叠加时，缓冲区超出了可用空间，系统无法编译。使用叠加后，缓冲区可以放入。然而，子系统之间以一种对不经意的观察者来说并不明显的方式相互依赖（因为你已经把封装性彻底打碎了）。

实现内存叠加有几种方法。最简单的是将缓冲区视为一个模块的私有资源，并通过单一函数允许访问，如第27页"创建接口"中描述的修改版单例模式。 另一种方法是实现多个数组的联合体，可能还附带一个所有者标记来指示当前内存的使用者。 或者，为了使子系统之间不那么纠缠，你可以修改链接器脚本，将RAM缓冲区彼此叠加。这消除了两个子系统之间的任何直接交互，但要求未来的任何开发者都明白这两个子系统不能同时运行（否则会带来灾难性的后果）。

需要更快的速度

在所有值得投入宝贵开发时间的地方中，最糟糕的可能是花在试图从处理器中多挤出几个周期上。尝试通过从系统设计之初就着手，也许在选择处理器时留出一些余量，来避免这种局面。然而，有时候你必须让代码运行得更快来响应实时事件、添加另一个功能，或降低功耗（见第13章）。 在深入进行认真的系统调优之前，先从对你的应用程序进行性能分析开始，以确保你聚焦在重要的部分上。性能分析不像阅读映射文件那么简单，但优化错误的东西仍然是不明智的（例如，把系统启动时只运行一次的初始化时间砍掉一半，而不是专注于主循环中的问题）。

性能分析

要知道在优化代码时把时间花在哪里，你需要知道处理器周期都去了哪里。许多编译器（和操作系统）都有一些内置的分析工具，包括性能分析器。如果你有这些工具，就去学习它们。如果没有，你可能需要构建自己的简易性能分析器来获得一些洞察。 在物理学中，海森堡不确定性原理指出，电子的动量和位置不能同时以任意精度确定。在性能分析中，也存在不确定性：你需要越精确地知道每段代码运行多长时间，你对整体执行情况的了解就越少。也就是说，你的分析器会改变代码的行为（和时序）。理解分析器对代码的影响是性能分析的一个重要部分。 性能分析通常从回答处理器时间花在哪里的问题开始。通过深入到特定函数中，你可以用同样的方法确定该函数的哪个部分最耗时（以此类推）。这里讨论的四种分析器各有关注点的细微差异，帮助你获得对系统的广泛而深入的了解。 与代码空间和RAM记分卡类似，使用你的分析器来跟踪哪些修改最有效。

优化处理器周期

有了对什么在拖慢系统的了解，你现在可以探索可用的选项了。一定要从打开编译器优化开始。你需要的手动调整越少，代码就越好。 接下来，尝试将大多数变量放入寄存器中。即使你有一个很长的函数调用链，变量在调用另一个函数时最终会放到栈上，但如果它们至少能在较小的作用域内存在于寄存器中，代码就会更快。 在完成了这些基础工作之后，考虑以下各节中的技术。

内存时序

等待状态是高效使用处理器资源的祸根。许多类型的内存无法以处理器运行的速度访问。要从这样的内存中获取信息，处理器必须等待一定数量的处理器周期来补偿时序差异。内存有一定数量的等待状态。例如，如果你的代码从具有四个等待状态的flash中运行，每次需要新的指令时，处理器都必须等待四个时钟周期。 我应该指出，四个等待状态的内存并不（总是）意味着你的代码运行速度比在一个等待状态的内存中慢四倍。处理器可以对指令进行流水线处理，以减少慢速内存的影响——换句话说，在执行当前指令的同时查找后续指令。如果流水线级数大于等待状态数，内存只会在流水线停顿（往往发生在分支处，如if语句和函数调用，因为处理器无法假设它会执行内存中的下一条指令）时拖慢执行速度。 通过了解每种类型的内存有多少等待状态，你可以选择通过将代码移到更快的内存中来加速执行。例如，你可能希望将关键函数复制到零等待状态的RAM中，如果它比正常的程序flash更快的话。如果你只是偶尔需要该函数，你可以用另一个缓冲区来叠加内存。当需要该函数时，将它从代码空间复制到RAM中（不过你需要做一些性能分析，确保复制的开销能被其在RAM中的惊人速度所抵消）。许多编译器支持关键字（ramfunc）、pragma或宏，让你可以指示该函数应该存储在代码空间中，但在启动时加载到RAM中（由在main之前运行的启动代码完成）。通常你需要修改链接器文件将该段放入RAM。请查阅你不常用的编译器手册，而不是你手边的处理器手册。

变量大小

当你在8位处理器上工作时，很容易理解使用更大的变量会带来更高的处理器周期成本。虽然可能看起来不太合逻辑，但在更大的处理器上使用更小的变量也可能带来一些不必要的开销。为了获得最佳结果，局部变量应该与寄存器的大小匹配。 当编译器需要将局部变量的大小从原生的32位变量缩小到8位char或16位short时，它必须进行符号扩展，这意味着 每次操作都需要两条指令（对于无符号变量，则需要一条额外的零扩展指令）。一直思考这种繁琐级别的优化是编译器的工作。然而，如果你通常使用原生类型来实现变量，你可以给它更好的提示。 同样，尽量在处理的大部分内容中使用相同类型的变量。类型转换是处理器时间的浪费。也应尽可能避免有符号与无符号之间的转换。 将有符号整数与无符号整数比较时，有符号整数会被提升为无符号整数。因此，当一个小的负值有符号变量被不明智地与无符号变量比较时，它很可能被认为是数值上更大的值。除非你真的需要负数，否则坚持使用无符号变量。

再看函数调用链

循环展开

到目前为止，当你查看这个函数中循环的汇编代码时，与零的比较可能是大约 10 条指令之一。bufLength 的递减是另一条。你花了 20% 的时间处理循环开销。 编译器无法消除这些开销，但你对情况了解更多。你对代码试图完成的任务有更多上下文。例如，你知道字节数是偶数（因为你是这样设计的）。没有必要在每次循环时都检查，只需每隔一次检查： void LcdWriteBuffer(uint16_t* buffer, uint16_t bufLength){ // 使用字节缓冲区。仅当字节序正确时才能正常工作。 uint8_t *byteBuffer = (uint8_t *) buffer; bufLength = bufLength*2; IoClear(LCD_SELECT_N);

// 选中芯片

向商科专业的人解释优化

归根结底，优化是一个经济学问题。你一开始拥有与系统相关的一组资产。主要的资产是 RAM、处理器周期和代码空间。你可能还有一些辅助资产，如功耗和处理器上的外设支持。你最流动的资产是开发时间，可以把它看作金钱。一旦你将这些资产投入（或分配）到系统的各个部分，你就失去了将它们用于其他子系统的机会。 如果你最初选择的投资组合没有带来预期回报，你可能会部分收回已消耗的资源，但为此你需要投入更多的开发时间。随着你沿着开发路径继续前进，切换分配变得越来越昂贵（也越来越不可能）。在设计过程开始时做出正确的决策，可能意味着在市场的底部买入与血本无归之间的区别。 为了做出真正有益的战略交易，你需要从资产和负债的角度理解你的资源。不幸的是，系统投资组合还不是一份邮寄到你手中的精美招股说明书。对它准确、精确的理解需要大量时间（即金钱）。估算对某些领域来说可以满足需求；其他领域则需要深入调查（性能分析）。 你的系统资产在一定程度上是可以互换的。例如，你可以用 RAM 换取处理器周期或代码空间（你需要一些开发时间来促成这笔交易）。有时你不需要交换任何东西，花费更多的开发时间就能减轻你的债务负担。然而，任何一种资源的总量是固定的，并且某种资源可能变得如此稀缺，以至于无论多少开发时间（和资产）都无法再产生更多。 当你考虑不同的优化策略时，也要考虑投入资产所带来的高机会成本。购买期货几乎总是比购买股票更便宜。同样，在设计阶段选择资源比等到最后一刻才意识到你严重负债且无法轻易挽回要便宜得多。

查找表

优化中没有什么是免费的。即使开启编译器优化也会消耗开发时间，因为调试器不再像以前那样工作了。当你逐行单步执行时，调试器不会显示大多数变量（那些被编译器移除的变量），而且它会跳来跳去（因为编译器重新排列了汇编指令）。 循环展开是以代码空间换取速度。使用宏代替函数也是以代码空间换取速度。这些权衡是双向的，所以如果你需要更多代码空间，你可能想要重新卷起循环并消除宏。 在周期和代码空间（或 RAM）之间还有另一种超越宏的权衡：查找表。查找表存储了对特定参数执行操作所需的值。当运行中的代码需要这些信息时，它不是执行计算，而是在表中查找结果，通常通过一个简单的索引。 举个简单的例子，如果你需要将 128 个 ASCII 字符转换为对应的 Unicode，你可以将它们放入表中来查找结果。然而，查找表的用途远不止于此。许多复杂的算法（例如，加密算法 AES）有两种实现：一种是使用查找表的快速、大型实现，另一种是计算所需值的慢速、小型实现。（生成查找表以减少数学开销在第 12 章中有详细讨论。） 查找表可以是基于代码的（值在编译时或编译前计算），也可以是基于 RAM 的。后者在 RAM 访问速度快（较少等待状态）或 RAM 充足但代码空间不足（在初始化时计算表）的情况下很有用。当查找值需要随情况变化而变化时（例如，网络路由器的查找表在需要不同协议时会改变），它们也很有用。 编译器可能在你使用 switch 语句代替 if-else 时创建查找表。查看你的汇编代码会告诉你它是否这样做了（以及这是否为你节省了资源）。

用汇编语言编写代码

查看你的汇编代码是优化的重要组成部分。即使你一开始不知道汇编语言中指令的含义，在调试器中跟踪关键函数将帮助你弄清楚处理器真正在做什么。一旦你理解了这一点，你可能能够调整你的高级语言代码，帮助编译器更高效地完成工作。 话虽如此，你的时间很宝贵。不要用汇编语言编程。真的，这不是一个好主意。生成的代码通常是一团糟，几乎总是从头重写比维护更容易，即使对原始程序员来说也是如此。这并不意味着它容易重写，只是说它可能无法阅读。汇编代码的维护通常以大规模重构的形式出现（也就是全部重写并修复旧错误，但无疑会引入新错误）。 然而，如果你有一个函数真的、真的需要超快，而编译器显然没有尽其所能，那么，用汇编编程可能是一种乐趣，就像在工作时偷偷玩俄罗斯方块一样。 从高级代码开始。理解编译器生成的汇编代码。接下来，打开优化并真正理解编译器生成的新汇编代码。你比编译器更聪明，而且你对系统的了解更多。但编译器几乎肯定比你更懂汇编语言。在开始调整编译器生成的汇编代码之前，先让它向你展示它认为重要的内容。 这就是最大的秘密：不要从空白开始。从编译器给你的汇编代码开始，然后在此基础上改进。将等效的高级代码作为注释粘贴到汇编代码中，以便将来的你能记住每个部分的目标。

总结

我无法提供一个全面的优化技术列表。它们取决于你的处理器和编译器。更重要的是，它们取决于你的需求和可用资源。我可以说，如果你已经到项目末尾，正在寻找廉价的方法将代码减少 40%，那么你严重误判了硬件资源的能力。但我也犯过同样的错误。 优化始于良好的设计，最好是留有少量余量的设计，以防未来的功能比你计划的更大、更慢、更消耗 RAM。即使在项目结束时，你也需要一些备用资源来修复 bug 和应对硬件变化。 在医疗和安全相关产品中，这个余量需要更大。重新编译代码是一个文书密集型过程，即使是微小的单行更改。如果你因为需要多一个字节的 RAM 或多几个处理器周期来实现更改而最终修改了 50 行代码，文书工作和测试会呈指数级增长。 虽然将资源尽可能减少有一些乐趣，但你会得到递减的回报。前 10% 的改进应该不太困难，但下一个 10% 可能需要两倍的时间（以此类推）。从一个目标开始，不要优化太多超出目标。 优化中存在权衡。你可以在子系统之间共享资源，但每次这样做，你的产品都会变得不那么健壮，对于下一个修改它的人来说也会变得更脆弱。没有什么比将项目交给另一个团队并解释他们永远不应更改子系统 X，因为它会改变子系统 Y 的精确时序更令人尴尬的了。 更好地利用开发时间的方法是寻找使用已被充分理解的算法进行优化的途径。继续阅读书籍（和博客）来寻找解决常见（和不那么常见）问题的方法。经过验证的算法非常值得投入时间。你不是重新发明轮子，而是改进别人的轮子。 最后一点：很多时候，系统调优被留到开发周期末尾，甚至是在第一次测试完成之后。我听说这样做的理论是，功能应该在调优之前先能正常工作。将系统保持在资源限制内的过程应该在系统开发过程中就计划好并持续维护。在产品发布前引入复杂的更改会导致系统不稳定。要权衡过早优化（例如，阅读所有汇编列表代码寻找编译器可以减少一条指令的地方）的风险与尽早进行优化以便能够充分测试并对其他设计决策产生影响的好处。

面试题：反转一个字节中的比特位

首先，在有限内存的情况下反转一个字节中的比特位。完成后，修改代码使其尽可能快（但没有内存限制）。

在面试环境中，我不介意面试者从一个简单的解决方案慢慢开始。优化应该排在正确性之后：

uint8_t SwapBitsInByte(uint8_t input) { uint8_t output=0; for (uint8_t i = 0; i < 8; i++) { // 对于字节中的每个比特位 if (input & (1 << i)) { // 需要在输出中设置该比特位 output |= 1 << (7-i); } } return output; } 一般来说，我在面试中不关注语法（那是编译器的工作）。然而，在这个问题中，括号很重要，因为位移运算符的优先级低于加法或减法。如果面试者漏掉了这一点，我会询问运算符优先级。不是每个人都记住了这些，但如果搞错了，它会在你的代码中造成严重破坏（还是到处使用括号吧，安全起见）。 理想情况下，程序员应该检查自己的代码，用几个值运行一遍以确保按照指令执行能正常工作。就像心理单元测试一样，我喜欢看到面试者在编写代码时（甚至之前）这样做。 当我审查解决方案时，命名很重要，包括函数名和变量名。注释只要有用就是好的（"// 在输出中设置比特位"在 if 语句上可能有用，但在实际设置比特位的代码行上可能就没必要了）。 使用变量来实现问题是一个好的开始，尽管有一种更直接的方法可以用一个变量完成（通过展开循环）。如果候选人提到两个变量（以及输入参数）很可能都在寄存器中，我可以指出使用额外寄存器可能意味着其他某个变量被推入了栈中。尽管有纠正，面试者因这个观察仍然会得到很多分。 至于问题的第二部分，我不认识有多少人在面试环境中成功解决了这个问题。这是那种你需要知道的技巧之一：使用查找表。如果你能分配 256 个字节（在 RAM 或代码空间中，以更快的为准），快速查找一个字节的反转值，你只需要将字节的值作为字节数组的索引： uint8_t SwapBitInByte(uint8_t input) { const uint8_t lookup_table[256] = {0x00, 0x80, 0x40, 0xC0... 0x7F, 0xFF}; return lookup_table[input]; } 这种技术在代码空间比时间更充裕的嵌入式场合中经常使用。我希望到这个时候，面试者已经提到他们会查找算法，以确保他们有一个针对设计约束的合理最优解。 对于问题的第一部分，还有一个更优的解法。不是使用临时变量逐个反转比特位，代码可以成对反转比特位，然后反转对，再反转半字节，全部不需要临时变量（我怀疑可以少用一个寄存器）： uint8_t SwapBitInByte(uint8_t val) { val = ( ( val & 0x55 ) << 1 ) | ( ( val & 0xAA ) >> 1 ); val = ( ( val & 0x33 ) << 2 ) | ( ( val & 0xCC ) >> 2 ); val = ( ( val & 0x0F ) << 4 ) | ( ( val & 0xF0 ) >> 4 ); return val; } 我不会期望面试者当场想出来。我是从 Henry S. Warren 的 Hacker's Delight（Addison-Wesley 出版）改编而来的。另一方面，现在我很想让未来的面试者解释这段代码做了什么（以及如何让它更快，希望他们会想到查找表）。
