使用核心转储

在核心转储中放入什么内容？一方面，放入你能容纳的一切。另一方面，在处理器处于脆弱状态时，尽量减少操作。 首先放入一个已知值来标识有效的核心转储（我们称之为核心转储密钥；它是什么并不重要，只要不是全零或全一即可）。 接下来，放入故障原因。经过手动调试之后，你应该已经找到了描述各种可能异常的手册。然后，记录出错时你在哪里。这可能意味着要解析栈跟踪，这本应很简单，但由于是在故障中进行的，通常会很复杂。真正的目标是找到一组返回地址（通常在 lr 链接寄存器中）。理想情况下，这应该包括栈指针和传入每个函数的参数。实际上，根据你的编译器和处理器的不同，追溯这些可能会非常痛苦。可能有一些特殊的编译器特性可以使栈展开变得更简单。 最后，如果还有空间，添加任何可能对你的系统重要的信息；我最喜欢的一项是最后的输入电压ADC读数，因为我曾需要调试低电量问题，最初却以为是代码灾难。

仅仅是"非常棘手"的Bug

很多人担心内存Bug，这理所当然。让指针出错的方式有很多种。在这方面很难建立信心。我愿意相信嵌入式软件相对简单一些，因为我们有真实的内存单元。你寻址的每一个东西都对应硅片上的一组实际晶体管。 然而，指针终归是指针。它们需要练习。因为你与现实之间至少相隔了一步，所以调试起来更加困难。我发现画图很有帮助——并且确保我打算做的事情与我所写的代码一致。

我的大多数内存Bug来自以下来源之一：

• 缓冲区溢出和差一错误（off-by-one），导致写入不属于我的内存 • 从函数返回局部内存导致的栈损坏 • 栈溢出，通常是由于递归或调用过多的函数 • 未初始化变量 我有一套调试内存问题的技巧。第一个是将变量设为静态（static）或全局（global），看看是否是栈问题（或未初始化变量的问题）。注意：如果问题因此而消失，问题并没有解决，只是被隐藏了；你仍然必须修复它。

第9章：陷入困境

其次，你可以在缓冲区之间添加额外的缓冲区（红色警戒区）。用已知值（如 0xdeadbeef 或 0xA5A5A5A5）填充这些区域。运行一段时间后，查看红色警戒区缓冲区中的数据是否被修改，这表明某个缓冲区超出了其边界。 你可以对栈做类似的事情：在启动时用已知数据填充它们，然后在运行相当长的时间后查看栈被使用了多少。栈达到的最高点（位于红色警戒区数据尚未被修改的边缘）称为高水位标记，代表栈的最大使用量。 如果你遇到了奇怪的问题，尝试增大栈的大小，看看问题是否出现得更慢。或者反过来，减小栈是否会更快地触发问题？复现Bug是从"不可能的Bug"走向"非常棘手"的重要一步。 最后，用固定缓冲区替代堆（malloc 和 new）缓冲区。这不仅能够避免使用已释放的内存，还可以缓解尝试分配过多内存（或在堆碎片化时尝试分配大块内存）的问题。

自作聪明的后果

如果说硬件故障是处理器发出的求助情书，那么编译器警告就是平凡无奇的交通标志。错过"禁止转弯"的标志，或者明知故闯黄灯，都是很容易发生的事。大多数情况下，忽略警告不会有什么严重后果，没什么大不了的。 然而，本章讨论的许多硬件故障，本来都可以通过启用所有编译器警告并逐一修复来发现。

花时间消除那些看似微不足道的编译器警告，这样你才能看到那些至关重要的警告：

hardfaults.c:51: 'ptr_uninitialized' is used uninitialized in this function hardfaults.c:78: function returns address of local variable 所以，当你复现了Bug、解释了Bug、并且尝试了你能想到的一切方法之后，也许可以回过头来清理那些积压已久的警告。或者更好的是，从一开始就不要让它们累积。 最后，你不是机器人。当你到达注意力的极限，陷入"一切都不行、都是我的错"的绝望深渊，或者再也想不出下一步该尝试什么时，休息一下。出去走走。吃点东西。和别人聊点别的事。睡一觉。你的潜意识需要时间和空间来处理问题，而不是由你不断地给它灌输更多关于问题的信息。

延伸阅读

在《终结嵌入式软件黑暗时代：让我们从处理器故障调试开始！》（"Ending the Embedded Software Dark Ages: Let's Start with Processor Fault Debugging!"）一文中，Embedded Artistry 的 Phillip Johnston 走过了整个调试过程，从手动分析硬件故障，到创建良好的处理程序，再到制作一个供后续使用的迷你核心转储。 该文章链接到 Interrupt Blog 的《如何调试 ARM Cortex-M MCU 上的 HardFault》（"How to Debug a HardFault on an ARM Cortex-M MCU"），这是最具战术性的动手实践资源。 关于栈和堆的更多细节，可参阅《为了乐趣和利益而粉碎栈》（"Smashing the Stack for Fun and Profit"）。 Miguel Young de la Sota 的文章《关于链接器脚本你从来不想知道的一切》（"Everything You Never Wanted to Know About Linker Script"）是一篇关于链接器文件的精彩文章。另一个很好的资源是 Thea Flowers 的文章《注释最详尽的链接器脚本（大概）》（"The Most Thoroughly Commented Linker Script (Probably)"）。

面试题：喘口气

我应该问你什么？ 有时候面试会变得非常糟糕。有时是因为候选人不合格，但有时候选人完全合格，只是过度紧张或者那天运气特别不好。面试令人疲惫不堪。赌注很高，失败的可能性也高得令人难以接受。 当面试明显偏离轨道时，我会问候选人我应该问他们什么。我想让他们谈谈自己熟悉的东西，谈谈他们想分享的东西。有些候选人会因此活跃起来，表现出他们对职位有兴趣和专长（只是不擅长面试过程而已）。 当人们问我从面试者的角度有什么策略时，我经常建议带一个项目作品去面试。这本质上是在他们带来的硬件上挂了一个大大的"问我这个！"的牌子。它让候选人能够控制面试的一部分，将对话的一部分引导到候选人理解并能够谈论的话题上。 无论是他们带来了项目，还是我决定在面试中喘口气，让候选人谈论他们的项目通常都能增强他们的信心。利用这个计划问题之间的短暂间歇，提醒自己：几乎没有人知道他们面试的岗位所需的一切知识。然而，他们可能拥有重要而有用的技能，甚至可能是比你原本认为需要的更重要的技能。
