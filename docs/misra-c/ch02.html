2.1 C语言的流行

C编程语言之所以流行，是因为：

• C编译器可广泛用于许多处理器；

• C程序可以编译成高效的机器代码；

• 它由国际标准定义；

• 它提供了访问目标处理器输入/输出能力的机制，无论是直接访问还是通过语言扩展；

• 在关键系统中使用C语言有相当丰富的经验；

• 它得到静态分析和测试工具的广泛支持。

2.2 C语言的缺点

虽然流行，但该语言存在若干缺点，以下各小节将进行讨论。

2.2.1 语言定义

该标准并未完全规定语言，而是将某些方面交由实现控制。这是有意为之，部分原因是希望支持针对不同目标处理器的众多现有实现。

因此，该语言中存在以下方面的区域：

• 行为是未定义的；

• 行为是未指定的；

• 实现可自由选择其自身行为，只要加以记录即可。

依赖未定义或未指定行为的程序不一定能保证以可预测的方式运行。

过度依赖实现定义行为的程序可能难以移植到不同的目标平台。如果无法配置分析器来处理实现定义行为，其存在也可能阻碍静态分析。

2.2.2 语言误用

虽然C程序可以以结构化和易于理解的方式布局，但C语言使程序员容易编写难以理解的晦涩代码。

运算符的规范使得编译器难以检测编程错误。例如，以下两个代码片段都是完全合法的，因此编译器不可能知道一个是否被错误地用于替代另一个：


if ( a == b )    /* 测试a和b是否相等 */
if ( a = b )     /* 将b赋值给a并测试a是否非零 */

2.2.3 语言误解

该语言中存在一些程序员普遍误解的区域。例如，C语言比其他一些语言有更多的运算符，因此有大量不同的运算符优先级级别，其中一些并不直观。

C语言提供的类型规则也可能使熟悉强类型语言的程序员感到困惑。例如，操作数可能被"提升"为更宽的类型，这意味着运算结果类型不一定与操作数的类型相同。

2.2.4 运行时错误检查

C程序可以编译成小巧高效的机器代码，但代价是运行时检查程度非常有限。C程序通常不为常见问题提供运行时检查，例如算术异常（如除零）、溢出、指针有效性或数组越界错误。C语言的理念是程序员负责显式地进行此类检查。

2.3 C语言在关键系统中的使用

尽管Ada仍在使用，但C编程语言已成为关键系统（无论是安全相关还是安保相关）中软件的事实标准选择，适用于嵌入式（独立运行）和宿主式应用程序。

本指南中的建议，如果在文档化的软件开发过程中使用，可以解决C语言的许多缺点，无论所开发代码最终用途的目的如何。

因此，这些指南在安保相关环境中与在安全相关环境中同样适用。

第3章 工具选择

3.1 C语言及其编译器

本文档的工作开始时，C语言的ISO标准是经过[9]、[10]和[11]更正的ISO/IEC 9899:1999 [8]。此版本的语言以下称为C99。然而，许多编译器仍适用于其前身，即经过[4]、[5]和[6]修正和更正的ISO/IEC 9899:1990 [2]所定义，以下称为C90。一些编译器提供在两个语言版本之间进行选择的选项。

C语言的当前ISO标准是经过[14]更正的ISO/IEC 9899:2011 [13]。该标准发布时，MISRA C指南的工作已接近完成，因此未能纳入此后续版本的指导。

注意：使用MISRA C不需要获取相关标准的副本，但可能会有所帮助。

在C90和C99之间的选择可能受到诸如项目中重用的遗留代码数量以及目标处理器编译器可用性等因素的影响。

为项目选择的编译器应符合所选C语言版本的符合性独立实现的要求。编译器可以超出这些要求，例如通过提供该语言的所有特性（独立实现只需提供定义良好的子集），或者提供语言标准允许的扩展。

理想情况下，编译器确实符合标准的确认应由编译器开发人员提供，例如通过提供所运行的符合性测试的详细信息和所获得的结果。

有时，可选的编译器可能有限，其质量可能未知。如果难以从编译器开发人员那里获取信息，可以采取以下步骤来协助选择过程：

• 检查编译器开发人员是否遵循适当的软件开发过程，例如满足ISO 9001:2008 [21]的要求（经ISO 90003:2004 [22]评估）；

• 阅读编译器评论和用户体验报告；

• 审查用户群规模和使用该编译器开发的应用程序类型；

• 执行并记录独立的验证测试，例如使用符合性测试套件或编译现有应用程序。

注意：某些过程标准要求在某些情况下对编译器进行资格认定，例如IEC 61508:2010 [32]、ISO 26262:2011 [23]和DO-178C [24]。

3.2 分析工具

仅通过检查就可以检查C源代码是否符合MISRA C。然而，这可能极其耗时且容易出错。因此，任何现实的对照MISRA C检查代码的过程都将涉及使用至少一种静态分析工具。

适用于编译器选择的所有因素也适用于静态分析工具的选择，尽管分析工具的验证与编译器的验证略有不同。理想的静态分析工具将：

• 检测所有违反MISRA C指南的情况；

• 不产生"误报"，即只报告真正的违规，不报告非违规或可能的违规。

由于第6.5节中解释的原因，现在——也永远不可能——生产出满足这一理想行为的静态分析工具。因此，在尽可能检测最大数量的违规同时最小化误报消息数量，是选择工具的重要因素。

有各种各样的工具可供选择，执行时间从几秒到几天不等。大体上说，消耗较少时间的工具比消耗大量时间的工具更有可能产生误报。在工具选择过程中还应考虑分析时间和分析精度之间的平衡。

分析工具的侧重点各不相同。有些可能是通用目的，而其他则专注于对潜在问题的子集进行全面分析。因此，可能需要使用多个工具来最大化问题覆盖率。

注意：某些过程标准，包括IEC 61508:2010 [32]、ISO 26262:2011 [23]和DO-178C [24]，要求在某些情况下对验证工具（如静态分析器）进行资格认定。

第4章 预备知识

4.1 培训

为确保C源代码的开发人员具有适当的技能和能力水平，应提供以下方面的正式培训：

• C编程语言在嵌入式应用程序中的使用；

• C编程语言在高完整性和安全相关系统中的使用。

由于编译器和静态分析工具是复杂的软件，还应考虑提供其使用方面的培训。对于静态分析工具，可能可以获得专门针对MISRA C使用的培训。

4.2 理解编译器

在本文档中，术语"编译器"（在ISO C标准[2]、[8]中称为"实现"）指编译器本身以及任何相关工具，如链接器、库管理器和可执行文件格式转换工具。

编译器可能提供各种控制其行为的选项。理解这些选项的效果很重要，因为它们的使用或不使用可能影响：

• 语言扩展的可用性；

• 编译器与ISO C标准的符合性；

• 程序所需的资源，特别是处理时间和内存空间；

• 编译器中缺陷被暴露的可能性，例如在执行复杂的高度优化代码转换时可能发生的情况。

理解编译器如何实现C语言中那些在ISO C标准中被称为"实现定义"的特性非常重要。理解编译器可能提供的任何语言扩展也很重要。

编译器开发人员可能维护一份已知影响编译器的缺陷列表以及任何可用的变通方法。在使用该编译器开始项目之前，了解此列表的内容显然是有利的。如果编译器开发人员不提供此类列表，则在发现缺陷或疑似缺陷并向编译器开发人员报告时，应维护一份本地列表。

4.3 理解静态分析工具

应对项目中所使用的每个静态分析工具的文档进行审查，以理解：

• 如何配置分析器以匹配编译器的实现定义行为，例如整数类型的大小；

• 分析器能够检查哪些MISRA C指南（第5.3节）；

• 是否可以配置分析器来处理将要使用的任何语言扩展；

• 是否可以调整分析器的行为以实现分析时间和分析精度之间的不同平衡。

工具开发人员可能维护一份已知影响工具的缺陷列表以及任何可用的变通方法。在使用该工具开始项目之前，了解此列表的内容显然是有利的。如果工具开发人员不提供此类列表，则在发现缺陷或疑似缺陷并向工具开发人员报告时，应维护一份本地列表。
