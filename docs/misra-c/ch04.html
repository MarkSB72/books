6.1 指南分类

每条MISRA C指南被分类为"规则"（rule）或"指令"（directive）。

指令是一种无法提供执行合规性检查所需的完整描述的指南。需要额外信息（例如可能在设计文档或需求规格说明中提供的信息）才能执行检查。静态分析工具可能有助于检查指令的合规性，但不同工具可能对什么构成不合规有广泛的不同的解释。

规则是一种已提供需求完整描述的指南。应该可以在不需要任何其他信息的情况下检查源代码是否符合规则。特别是，静态分析工具应能够检查规则的合规性，但要受第6.5节所述限制的约束。

第7节包含所有指令，第8节包含所有规则。

6.2 指南类别

每条MISRA C指南被赋予单一类别："强制性"（mandatory）、"要求性"（required）或"建议性"（advisory），其含义如下所述。除这一基本分类外，本文档不给出、也不意图暗示每条指南的任何重要性等级。所有要求性指南（无论是规则还是指令）应被视为同等重要，所有强制性和建议性指南也应如此。

6.2.1 强制性指南

声称符合本文档的C代码应遵守每条强制性指南——不允许偏离强制性指南。

注意：如果检查工具产生诊断消息，这并不一定意味着指南被违反，其原因见第6.5节。

6.2.2 要求性指南

声称符合本文档的C代码应遵守每条要求性指南，在不遵守的情况下需要按照第5.4节所述进行正式偏离。

组织或项目可以选择将任何要求性指南视为强制性指南。

6.2.3 建议性指南

这些是建议。然而，"建议性"状态并不意味着这些项目可以被忽略，而是应在合理可行的情况下尽量遵循。建议性指南不需要正式偏离，但如果未遵循正式偏离程序，应做出替代安排来记录不合规情况。

组织或项目可以选择将任何建议性指南视为强制性或要求性指南。

6.3 指南组织

指南按C语言中的不同主题组织。然而不可避免地存在重叠，一条指南可能与多个主题相关。在这种情况下，指南被放置在最相关的主题下。

6.4 指南中的冗余

本文档中存在少数情况，其中给出的指南引用了文档其他部分被禁止或建议反对的语言特性。这是有意为之。可能是用户选择使用该特性，要么通过针对要求性指南提出偏离，要么通过选择不遵循建议性指南。在这种情况下，约束该特性使用的第二条指南就变得相关。

6.5 规则的可判定性

每条强制性、要求性和建议性规则被分类为可判定（decidable）或不可判定（undecidable）。此分类描述了静态分析器在理论上回答"此代码是否符合此规则？"这一问题的能力。指令不以此方式分类，因为仅凭源代码不可能设计出能保证检查合规性的算法。

如果程序能够在每种情况下以"是"或"否"来回答该问题，则该规则是可判定的，否则为不可判定的。作为此分类基础的计算理论的回顾超出了本文档的范围，但如果检测违规依赖于运行时属性，如：

• 对象持有的值；

• 控制是否到达程序中的特定点，

则该规则很可能不可判定。

可判定规则在静态分析方面具有有用的属性。如果无缺陷且完整的静态分析器被正确配置：

• 报告的可判定规则违规表示真实的违规；

• 没有报告的可判定规则违规表示所分析代码中没有违规。

可判定规则的一些示例包括：

• Rule 5.2：依赖于标识符的名称和作用域；

• Rule 11.3：依赖于源指针和目标指针类型；

• Rule 20.7：依赖于宏展开结果的语法形式。

静态分析器在检测不可判定规则违规方面的能力各不相同：

• 报告的不可判定规则违规不一定表示真实的违规；一些分析器采取报告可能违规的方式，以提醒用户不确定性；

• 没有报告的不可判定规则违规不一定表示所分析代码中没有违规。

不可判定规则的一些示例包括：

• Rule 12.2：依赖于移位运算符右操作数的值；

• Rule 2.1：依赖于知道执行是否永远不会到达某一点。

应制定过程来分析静态分析结果并记录结果。应特别关注分析与不可判定规则相关的任何输出的过程。

6.6 分析范围

每条规则根据检测违规所需检查的代码量进行分类。与可判定性一样，分析范围的概念不适用于指令。

适用于规则的分析范围是"单个翻译单元"（Single Translation Unit）和"系统"（System）。

如果规则被分类为可在"单个翻译单元"基础上检查，则可以通过独立检查每个翻译单元来检测项目内的所有违规。例如，一个翻译单元中存在不包含default标签的switch语句（Rule 16.4），不影响其他翻译单元是否包含此类switch语句。

如果规则被分类为需要在"系统"基础上检查，则识别翻译单元内的规则违规需要检查的不仅仅是该翻译单元。分类为"系统"的规则最好通过分析所有源代码来检查，尽管在检查整个源代码的子集时也可以识别某些违规。例如，如果一个项目有两个翻译单元A和B，可以检查每个翻译单元内对象的所有声明和定义是否使用相同的类型名称和限定符（Rule 8.3）。然而，这并不能保证A中的声明和定义与B中的使用相同的类型名称和限定符。因此，需要检查将被编译和链接到可执行文件中的所有源代码，以保证符合此规则。

所有不可判定规则都需要在"系统"基础上检查，因为在一般情况下，需要关于其他翻译单元行为的信息。例如，在下面的函数g中，自动对象x的值是否在x被使用之前被设置（Rule 9.1），将取决于在另一个翻译单元中定义的函数f的行为：


extern void f ( uint16_t *p );

uint16_t y;


void g ( void )

{

uint16_t x; /* x未被赋值 */

f ( &x ); /* f可能修改其参数所指向的对象 */

y = x; /* x可能已被设置，也可能未设置 */

}

6.7 多组织项目

项目可能涉及来自不同组织的代码，例如：

• 来自编译器实现者的标准库代码；

• 来自设备供应商的底层驱动代码；

• 来自专业供应商的操作系统和高级驱动代码；

• 可能根据合作组织的专长共享的应用程序代码。

标准库代码可能关注执行效率。它可能依赖实现细节或未指定行为，例如：

• 将对象类型指针强制转换为其他对象类型指针；

• 栈帧的布局，特别是这些帧中函数参数的位置；

• 在C中嵌入汇编语言语句。

由于它是实现的一部分，且其功能和接口在标准中定义，标准库代码不需要符合MISRA C。除非在各条指南中另有规定，标准头文件的内容以及在处理标准头文件期间包含的任何文件不需要符合MISRA C。然而，依赖于标准头文件声明和宏提供的接口的指南仍然适用。例如，基本类型规则适用于传递给标准库中指定函数的参数类型及其结果。

所有其他代码应最大程度地符合MISRA C指南。如果所有源代码都可用，则可以检查整个程序的合规性。然而，在许多项目中，开发组织无法获得所有源代码。例如，合作组织可能共享功能规格说明、接口规格说明和目标代码，但可能通过不共享源代码来保护自己的知识产权。当只有部分源代码可用于分析时，应采用其他技术来确认合规性。例如：

• 提供商业代码的组织可能愿意发布MISRA C合规性声明；

• 合作组织可能：

-- 就每个组织将应用于自己源代码的通用程序和工具达成一致；

-- 相互提供源代码的桩版本，以允许进行跨组织检查。

项目应定义其将使用以下哪种方法来处理其他组织提供的代码：

1. 以与内部开发代码相同的方式处理——这依赖于拥有源代码；

2. 以与标准库相同的方式处理——这依赖于组织提供适当的MISRA C合规性声明；

3. 对头文件及其接口的内容执行合规性检查——这假设没有合规性声明可用，且除头文件外没有源代码可用。

在第(3)种情况下，应在使用代码之前采用适当的额外验证和确认技术。

注意：某些过程标准可能包括管理多组织开发的更广泛要求，例如ISO 26262 [23]第8部分第5条"分布式开发中的接口"。

6.8 自动生成代码

MISRA C指南适用于自动生成的代码。合规性的责任既在于自动代码生成工具的开发人员，也在于生成代码所基于的模型的开发人员。由于存在多个建模包，每个建模包可能有多個自动代码生成器，因此无法为每条MISRA C指南单独分配责任。期望建模包和代码生成器的用户将采用相关指南，如MISRA AC GMG [17]、MISRA AC SLSF [18]和MISRA AC TL [19]。

应用于自动生成代码时分配给MISRA C指南的类别不一定与应用于手工编写代码时的类别相同。在进行此区分时，重要的是注意某些建模包允许将手工编写的代码注入到模型中。在确定适用的指南类别时，此类代码不被视为自动生成。

附录E列出了那些应用于自动生成代码时其类别与手工编写代码不同的MISRA C指南。它还说明了自动代码生成器开发人员需要满足的文档要求。

6.9 指南的呈现方式

本文档的各条需求以如下格式呈现：

标识符（Ident）

需求文本（Requirement text）

[源引用（Source ref）]

类别（Category）

分析（Analysis） 可判定性（Decidability），范围（Scope）

适用于（Applies to） Cxx

其中：

• "标识符"是指南的唯一标识符；

• "需求文本"是指南本身；

• "源引用"表示导致此项或此组项目的主要来源（如适用）。关于这些引用的重要性说明以及源材料的索引，见第6.10节；

• "类别"是"强制性"、"要求性"或"建议性"之一，如第6.2节所述；

• "可判定性"是"可判定"或"不可判定"之一，如第6.5节所述；

• "范围"是"系统"或"单个翻译单元"之一，如第6.6节所述；

• "Cxx"是"C90"和/或"C99"（以逗号分隔），指示指南适用于C语言的哪些版本。

注意：由于指令没有可判定性或分析范围，指令省略"分析"行。

此外，为每个项目或相关项目组提供支持性文本。该文本在适当的情况下给出指南所处理的基本问题的一些解释，以及如何应用指南的示例。

在支持性文本中，可能有标题为"详述"（Amplification）的部分，后跟提供指南更精确描述的文本。详述是规范性的；如果它与标题冲突，则以详述为准。这种机制很方便，因为它允许用简短的标题传达复杂的概念。

在支持性文本中，可能有标题为"例外"（Exception）的部分，后跟描述规则不适用的情形的文本。例外的使用允许简化某些指南的描述。重要的是注意，例外是指南不适用的情况。凭借例外而符合指南的代码不需要偏离。

支持性文本不旨在作为相关语言特性的教程，因为假设读者具有该语言的工作知识。关于语言特性的更多信息可通过查阅标准的相关章节或其他C语言参考书获得。当为标准的"可移植性问题"中列出的一个或多个问题给出源引用时，其中提出的原始问题可能有助于理解该指南。

在指南及其支持性文本中，使用以下字体样式表示C关键字和C代码：

• C关键字以斜体文本出现；

• 术语表中定义的项以斜体文本出现；

• C代码以等宽字体出现，可在其他文本中；

• 或以独立代码片段出现。

注意：在引用代码时，片段可能不完整（例如没有体的if语句）。这是为了简洁起见。

在代码片段中，假定了以下typedef类型（这是为了符合Dir 4.6）：

uint8_t /* 无符号8位整数 */

uint16_t /* 无符号16位整数 */

uint32_t /* 无符号32位整数 */


int8_t    /* 有符号8位整数 */
int16_t   /* 有符号16位整数 */
int32_t   /* 有符号32位整数 */
float32_t /* 32位浮点数 */
float64_t /* 64位浮点数 */

非特定对象名称的构造方式可表明其类型。例如：

uint8_t u8a; /* 8位无符号整数 */


int16_t  s16b;  /* 16位有符号整数 */
int32_t  s32c;  /* 32位有符号整数 */

bool_t bla; /* 基本布尔类型 */


enum atag ena;  /* 枚举类型 */
char     chb;   /* 字符 */
float32_t f32a; /* 32位浮点数 */
float64_t f64b; /* 64位浮点数 */

6.10 理解源引用

当指南源自一个或多个已发布的来源时，在指南后用方括号标明。这有两个目的。首先，希望更全面理解指南背后理由的读者（例如在考虑偏离请求时）可以查阅具体来源。其次，关于标准中描述的可移植性问题，引用的形式提供了关于问题性质的额外信息。

没有源引用的规则可能源自贡献公司的内部标准，或由审查人员建议，或被广泛接受的良好实践。

6.10.1 ISO C可移植性问题引用

当指南基于标准的附录G（C90）或附录J（C99）的问题时，读者理解未指定（Unspecified）、未定义（Undefined）、实现（Implementation）和区域（Locale）引用之间的区别是有帮助的。这里简要解释，更多信息可在Hatton [3]中找到。

6.10.1.1 未指定（Unspecified）

这些是必须成功编译的语言结构，但编译器编写者在结构的功能方面有一些自由度。例如Rule 13.2中描述的"求值顺序"。

虽然使用某些未指定行为是不可避免的，但不明智的做法是假设编译器产生的目标代码以特定方式运行；编译器甚至不需要在所有可能的结构中保持一致。

MISRA C识别出可能导致不安全行为的未指定行为的具体实例。

6.10.1.2 未定义（Undefined）

这些本质上是编程错误，但编译器编写者没有义务提供错误消息。例如函数的无效参数，或实参与定义的形参不匹配的函数。

从安全角度来看，这些特别重要，因为它们代表的编程错误可能不一定被编译器捕获。

6.10.1.3 实现（Implementation）

这些类似于"未指定"问题，主要区别在于编译器编写者必须采取一致的方法并加以记录。换句话说，功能可能因编译器而异，使代码不可移植，但在任何一个编译器上行为应该是定义良好的。例如整数除法和取余运算符（/和%）应用于一个正数和一个负数时的行为。

从安全角度来看，实现定义的行为往往不太关键，前提是编译器编写者已完全记录了预期的方法并一致地实现。建议尽可能避免这些问题。

6.10.1.4 区域（Locale）

区域特定行为构成一小部分特性，可能随国际需求而变化。例如用","字符代替"."字符表示小数点的功能。本文档不处理源自此来源的任何问题。
