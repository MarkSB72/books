C语言的类型安全问题

ISO C可以被认为表现出较差的类型安全性，因为它允许大量隐式类型转换发生。这些类型转换可能危及安全性，因为其实现定义的行为方面可能导致开发者困惑。

C.1.2 显式转换

显式类型转换（强制转换）可能出于功能原因引入：

•

为了改变后续算术运算执行的类型；

•

为了故意截断一个值；

•

为了清晰起见使类型转换显式化。

ISO C不要求检查所有显式强制转换，允许在不兼容类型之间进行转换。

C.1.3 转换的担忧

隐式和显式转换可能导致若干担忧，包括：

•

值丢失：例如转换为一个无法表示该值大小的类型；

•

符号丢失：例如从有符号类型转换为无符号类型导致符号丢失；

•

精度丢失：例如从浮点类型转换为整数类型导致精度丢失；

•

布局丢失：例如从某种类型的指针转换为不同类型指针导致不兼容的存储布局。

虽然许多类型转换是安全的，但能保证对所有数据值和所有可能的合规实现都安全的转换只有：

•

将整数值转换为相同符号性的更宽整数类型；

•

将浮点类型转换为更宽的浮点类型。

根据实现的整数大小，其他类型转换也可能是安全的。然而，任何潜在危险的类型转换应通过使其显式化来标识。

C.2

由于类型实现的大小可能因实现而异，隐式转换发生的上下文也可能变化。这要求开发者为任何特定项目维护所用类型系统的思维模型。开发者很容易不时使用错误的模型，尤其是当他们同时在具有不同实现的多个项目上工作时。

C语言如标准所定义包含许多弱点和矛盾，不幸的是，表达式的标准类型并不总是完全描述所表示数据的本质特性。例如：

•

整数提升 整数类型集的行为不一致。由于整数提升，本质上无符号的表达式（例如 unsigned char + unsigned char）通常具有 signed int 的标准类型。

•

整型常量 整型常量仅存在于 signed/unsigned int、long 和 long long 类型。这使确保类型一致性的问题复杂化（例如将常量作为函数参数传递时）。

•

字符常量 字符常量（例如 'x'）的标准类型被定义为 int（而非 char）。这模糊了字符数据（即"字符"）和数值数据（即"数字值"）之间的区别。

•

逻辑表达式 C90语言中不存在布尔类型。_Bool 类型被引入C99，但不幸的是，出于向后兼容的原因，相等（==, !=）、关系（<, <=, >=, >）和逻辑（&&, ||, !）运算符的结果仍然是 int 类型而非 _Bool 类型。

•

位域 ISO C未定义位域类型。这意味着例如无法强制转换为位域类型。ISO C定义的位域标准类型是 _Bool、signed int 或 unsigned int 之一。int 类型位域的有符号性是实现定义的。

•

枚举 枚举具有实现定义的类型。实现可以自由使用任何能够表示该枚举的整数类型。如果枚举包含负值，则类型将为有符号整数类型。如果枚举仅由非负值组成，则类型可以是有符号或无符号整数类型。

•

枚举常量 无论用于实现枚举的类型是什么，枚举常量始终是 int 类型。

I.1 摘要

MISRA C:2012规则10.6的原理是避免开发人员对某些算术运算发生的类型产生困惑。不幸的是，由于本项目所用编译器的一个"特性"，在不导致严重运行时性能下降的情况下无法使代码符合该规则。其影响是软件的时序要求无法在所有情况下满足，且存在车辆法定碳氢化合物排放目标无法达成的重大风险。

I.2 详细描述

本项目使用了多个可变时间步长积分器，用于累积多精度长期和。被积分的量和积分时间步长都是16位无符号量，需要相乘得到32位结果，然后进行累加。

由于本项目使用的C编译器以32位实现int类型，计算32位乘积的代码如下：


extern uint16_t qty, time_step;

uint32_t prod = ( uint32_t ) qty * ( uint32_t ) time_step;

显然，即使乘法运算符的操作数是32位的，乘积也不可能超过32位，因为两个操作数都是从16位零扩展而来的。

根据我们的标准开发流程，所有目标模块都通过最坏情况执行时间分析工具，以确保每个函数满足架构设计中规定的执行时间预算。分析器指出为这些积分器生成的代码远远超出了为其设定的预算。调查发现，执行时间过长的原因是编译器生成了对"移位相加"风格长乘法例程的调用。这令人惊讶，因为处理器配备了IMUL指令，能够在单个时钟周期内将两个16位无符号整数相乘得到32位结果。尽管乘法操作数是32位的，编译器有办法知道这些操作数的高16位为0，因此应该能够选择IMUL指令。

对编译器的实验表明，只要乘法操作数从16位隐式转换为32位，它就会选择IMUL指令，即：

uint32_t prod = qty * time_step;

I.3 理由

由于此类积分器在项目中的多个函数中使用，且平均每100微秒至少执行一次，库函数的性能不可接受。在指定的CPU内部频率25 MHz下，这意味着仅这些乘法就占用了4%的时间。这本身并不显著，可以包含在整体时序预算的余量中。然而，设计要求积分器在最长10微秒内提供结果，以满足其他函数的时序要求。未能满足此要求意味着实现排放目标存在重大风险，其商业影响超过1000万美元。

我们对此问题的首选解决方案是使用隐式转换编写积分器。这需要对MISRA C:2012规则10.6进行偏离。该代码在功能上与MISRA兼容代码生成的代码相同，但执行速度快达100倍。

这特别奇怪，因为C标准描述的代码行为与转换是隐式还是显式无关。无论乘法使用IMUL还是库调用，程序都会生成相同的结果，但库调用需要最坏情况下100个周期才能执行。编译器供应商已书面确认这是他们在该情况下预期的行为。

考虑了以下其他选项：

I.4

• 提高时钟速度——要达到所需性能需要将时钟提高10倍，但处理器的最大PLL频率为100 MHz；

• 更换处理器——在硬件设计验证已深入进行的情况下商业上不可行；项目的额外成本约为25万美元，并且还会有时序影响；

• 更换编译器——没有其他商业认可的该处理器编译器；有一个不受支持的公共领域编译器，但被认为不适合本项目；

• 重写库例程——该库使用基数为2的长乘法；可以重写为使用3条IMUL指令实现基数为65536的长乘法，但我们不愿修改编译器供应商的代码；我们已就此方法征求他们的意见，得到的回复是"他们不支持我们修改他们的库"。

请求偏离的条件

此偏离适用于项目中所有可变时间步长积分器实例。

I.5

不符合的后果

在本偏离记录所述情况下，不符合MISRA C:2012规则10.6没有任何后果。

此偏离不会产生额外的验证和确认要求。

I.6

控制报告的措施

用于检查此规则合规性的MMMC工具提供了一个功能，可以在表达式内抑制诊断消息。由于所有积分器都采用以下形式：

prod = qty * time_step;

可以使用宏来实现积分器并抑制警告。以下宏将用于实现乘法并将其结果赋值给乘积项：

/* Violates Rule 10.6: See deviation R_00102 */


#define INTEG(prod, qty, time_step) \

( /* -mmmc-R10_6 */ (prod) = (qty) * (time_step) /* -mmmc-pop */ )

虽然此宏可以实现为函数，但鉴于所执行操作的简单性，调用和返回的开销过大。因此在此情况下宏优于函数，即使这意味着违反Dir 4.9。

附录J：术语表

赋值（Assigned）

如果一个表达式是赋值操作的主体，则称其为被赋值的。

赋值（Assignment）

有时使用术语"赋值"来表示任何如同通过赋值完成的操作。此术语涵盖的操作包括：

• 通过赋值运算符之一进行赋值；

• 将参数传递给函数，此时参数如同通过赋值复制到相应的形参；

• 从函数返回表达式，此时结果如同通过赋值复制到具有函数返回类型的对象；

• 使用表达式初始化对象的全部或部分，包括C99中的复合字面量，此时表达式如同通过赋值复制到目标位置。

代码（Code）

代码由翻译单元中未被条件编译排除的所有内容组成。

死代码（Dead code）

其结果不影响程序行为的任何操作都是死代码。

注意：初始化与赋值操作不同，因此不是死代码的候选对象。

死代码的示例包括：

• 将值存储到从未后续使用的非volatile对象中；

• 不给对象赋值的表达式语句。

以下绝不是死代码：

• 访问volatile对象；

• 使用语言扩展。

由于操作发生的时间通常是嵌入式程序行为的重要方面，因此效果是插入延迟的代码不是死代码。但是，任何此类代码很可能都是参照定时器硬件编写的，因此无论如何都会涉及volatile对象访问。例如：


extern const volatile uint16_t MILLISEC_TIMER;
void delay_ms ( uint16_t n )

{

uint16_t start_time = MILLISEC_TIMER;


  while ( ( MILLISEC_TIMER - start_time ) < n )

{


    /* wait */

}

}

外部标识符（External identifier）

外部标识符是具有外部链接的标识符，因此必须表示对象或函数。

头文件（Header file）

头文件是作为#include指令目标的任何文件。

注意：文件扩展名不重要。

内联函数（Inline function）

内联函数是使用inline函数说明符声明的函数。

循环计数器（Loop counter）

循环计数器在第8.14节中定义。

宏标识符（Macro identifier）

宏标识符是作为宏名称或宏参数的标识符。

不透明类型（Opaque type）

实现细节不向其使用者公开的类型。

持久副作用（Persistent side effect）

如果副作用在执行的某个特定点可能对该点的执行状态产生影响，则称其为持久的。程序中给定点以下所有副作用都是持久的：

• 修改文件；

• 修改对象；

• 访问volatile对象。

当调用函数时，它可能产生副作用。修改文件或访问volatile对象从调用函数的角度看是持久的。然而，被调用函数修改的任何对象，如果其生命周期在函数返回时已结束，则不影响调用者的执行状态。修改此类对象产生的任何副作用从调用者的角度看不是持久的。

判断函数是否具有持久副作用时不考虑参数或其他非局部对象的可能值。

例如：

uint16_t f ( void )

{

uint16_t temp = 1;


  return ( temp );

}

x = f ( );

/* 修改temp的副作用对调用者不是持久的 */

项目（Project）

项目由用于构建单个可执行文件的一组翻译单元的代码组成。典型的嵌入式控制器可能包含多个逻辑上不同的项目，例如：

• 主引导加载程序；

• 辅助引导加载程序；

• 主应用程序。

原型形式（Prototype form）

如果函数类型包含原型（即指定参数类型列表，可选地包含名称），则称其为原型形式。例如，以下都是原型形式：


void f ( void );    /* 指定无参数的原型 */
void g ( int16_t, char );  /* 指定类型但不指定名称的原型 */
void h ( uint32_t n );     /* 指定类型和名称的原型 */

以下不是原型形式：


void f ( );          /* 没有参数信息 */


void g ( x, y )      /* "K&R"风格函数定义 */
int16_t x;
char y;

{

}

标准类型（Standard type）

表达式的标准类型是根据标准确定的类型。

不可达代码（Unreachable code）

如果不存在硬件故障且忽略未定义行为的影响，没有任何程序输入组合能够导致其执行，则代码是不可达的。

不可达代码可能源于程序控制流图的结构。例如，return语句之后的任何代码都是不可达的，逻辑运算符或条件运算符的某些操作数可能是不可达的：

uint16_t y;

uint16_t f ( void )

{

uint16_t x;


  return true ? y : ( y + 1U );  /* y + 1 从不执行 */

x = 10U; /* 此语句从不执行 */

}

不可达代码也可能出现在存在到达某语句的控制流路径但该路径永远无法被遵循时，例如：

uint16_t x, y;


switch ( 2u * x )

{


  case 0:
    y = 10u;
    break;
  case 1:
    y = 0u;      /* 不可达：2 * x 不可能为奇数 */
    break;
  case 2:
    y = x;
    break;

default:


    break;

}

被使用（Used）

如果一个表达式出现在以下任一上下文中，则称其为被使用的：

• 运算符的操作数，包括函数调用运算符的参数；

• if、while、for、do … while或switch语句的控制表达式；

• return语句返回的值；

• 初始化器。

此术语不应与读取对象的值混淆，例如：

uint16_t x = 3; /* x被使用但未被读取 */

uint16_t *p = &x;


return *p;             /* x被读取但未被使用 */
