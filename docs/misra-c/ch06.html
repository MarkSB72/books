8.1 标准C环境

Rule 1.1 程序应不包含违反标准C语法和约束的情况，且不应超出实现的翻译限制

[MISRA Guidelines Table 3], [IEC 61508-7: Table C.1], [ISO 26262-6: Table 1]

类别：要求性（Required）

分析：可判定（Decidable），单个翻译单元（Single Translation Unit）

适用于：C90, C99

详述（Amplification）

程序应仅使用所选版本标准（见第3.1节）中规定的C语言及其库的特性。

标准允许实现提供语言扩展，使用此类扩展是本规则允许的。

除非使用语言扩展，程序不应：

• 包含标准中描述的语言语法的任何违反；

• 包含标准施加的约束的任何违反。

程序不应超出实现施加的翻译限制。最小翻译限制由标准指定，但实现可提供更高的限制。

注意：符合标准的实现对语法和约束违规生成诊断，但要注意：

• 诊断不一定是错误，例如可以是警告；

• 尽管存在语法或约束违规，程序可能被翻译并生成可执行文件。

注意：当超出翻译限制时，符合标准的实现不需要生成诊断；可能生成可执行文件，但不保证正确执行。

理由（Rationale）

在制定本指南的过程中，未考虑与所支持ISO/IEC 9899版本之外的语言特性相关的问题。

有一些轶事证据表明某些不符合标准的实现未能诊断约束违规，例如[38]第135页示例2，题为"Error of writing into the const area"。

示例

某些C90编译器使用__inline关键字提供对内联函数的支持。使用__inline的C90程序将符合本规则，前提是它旨在使用此类编译器进行翻译。

许多嵌入式目标编译器提供额外的关键字，为对象所在内存区域的属性限定对象类型，例如：

• __zpage — 对象可以使用短指令访问

• __near — 指向对象的指针可以保存在16位中

• __far — 指向对象的指针可以保存在24位中

使用这些额外关键字的程序将符合本规则，前提是编译器支持这些关键字作为语言扩展。

Rule 1.2 不应使用语言扩展

类别：建议性（Advisory）

分析：不可判定（Undecidable），单个翻译单元（Single Translation Unit）

适用于：C90, C99

理由（Rationale）

依赖语言扩展的程序可能比不依赖的可移植性更差。尽管标准要求符合标准的实现记录其提供的任何语言扩展，但存在该文档可能不能在所有情况下提供完整的行为了描述的风险。

如果不应用此规则，使用每个语言扩展的决定应在项目的设计文档中说明理由。确保每个扩展有效使用的方法（例如检查编译器及其诊断）也应记录在案。

认识到在嵌入式系统中使用语言扩展是必要的。标准要求扩展不改变任何严格符合程序的行为。例如，编译器可能作为扩展实现对二元逻辑运算符的完全求值，即使标准规定一旦可以确定结果就停止求值。这样的扩展不符合标准，因为逻辑AND运算符右操作数中的副作用将总是发生，导致不同的行为。

Rule 1.3 不应出现未定义或关键未指定行为

类别：要求性（Required）

分析：不可判定（Undecidable），系统（System）

适用于：C90, C99

详述（Amplification）

某些未定义和未指定行为由特定规则处理。本规则防止所有其他未定义和关键未指定行为。附录H列出了未定义行为和那些被认为关键的未指定行为。

理由（Rationale）

任何导致未定义或未指定行为的程序都可能不以预期方式运行。在许多情况下，效果是使程序不可移植，但也可能发生更严重的问题。例如，未定义行为可能影响计算的结果。如果软件的正确运行依赖于此计算，则系统安全可能受到损害。如果未定义行为仅在极少情况下显现，该问题尤其难以检测。

MISRA C指南中的许多条目旨在避免某些未定义和未指定行为。例如，符合Rule 11.4、Rule 11.8和Rule 19.2确保在C中不可能创建指向声明为const限定类型对象的非const限定指针。这避免了C90 [Undefined 39]和C99 [Undefined 61]。然而，其他行为没有被特定指南覆盖，例如因为：

• 该行为不太可能遇到；

• 除了应避免该行为的明显陈述外，无法给出任何实际指导。

与其为每种未定义和关键未指定行为引入一条指南，MISRA C指南直接处理那些被认为最重要且最可能在实践中发生的行为。那些没有特定指南的行为全部由这一条规则涵盖。附录H列出了所有未定义和关键未指定行为，以及防止其发生的MISRA C指南。因此，它指出了哪些行为预期由本规则防止，哪些行为由其他规则涵盖。

注意：某些实现可能为标准中列出的一些未定义和未指定行为提供定义良好的行为。如果依赖此类定义良好的行为（包括通过语言扩展），则需要对本规则在这些行为方面进行偏离。

8.2 未使用代码

Rule 2.1 项目不应包含不可达代码

[IEC 61508-7 Section C.5.9], [DO-178C Section 6.4.4.3.c]

类别：要求性（Required）

分析：不可判定（Undecidable），系统（System）

适用于：C90, C99

理由（Rationale）

如果程序不表现出任何未定义行为，不可达代码无法执行，也不能对程序输出产生任何影响。因此，不可达代码的存在可能表明程序逻辑中存在错误。

编译器允许移除任何不可达代码，尽管它不必这样做。未被编译器移除的不可达代码浪费资源，例如：

• 占用目标机器内存空间；

• 其存在可能导致编译器在围绕不可达代码转移控制时选择更长、更慢的跳转指令；

• 在循环内，它可能阻止整个循环驻留在指令缓存中。

有时为了处理异常情况，插入看似不可达的代码是可取的。例如，在switch语句中，控制表达式的每个可能值都由显式case覆盖的情况下，根据Rule 16.4必须存在default子句。default子句的目的是捕获通常不应发生但可能由于以下原因产生的值：

• 程序中存在的未定义行为；

• 处理器硬件故障。

如果编译器能证明default子句不可达，它可能将其移除，从而消除防御动作。假设防御动作很重要，则需要证明编译器尽管代码不可达但不会消除该代码，或采取措施使防御代码可达。前一种做法需要对本规则进行偏离，可能通过审查目标代码或单元测试来支持此类偏离。后一种做法通常可以通过volatile访问来实现。例如，编译器可能确定x持有的值范围已被switch语句中的case子句覆盖，如：

uint16_t x;


switch ( x )

通过强制x通过volatile限定的左值访问，编译器必须假设控制表达式可以取任何值：


switch ( *( volatile uint16_t * ) &x )

注意：被预处理指令有条件排除的代码不受本规则约束，因为它不会呈现给后续翻译阶段。

示例


enum light { red, amber, red_amber, green };


enum light next_light ( enum light c )

{


  enum light res;
  switch ( c )

{


    case red:       res = red_amber; break;
    case red_amber: res = green;     break;
    case green:     res = amber;     break;
    case amber:     res = red;       break;
    default:
    {
      /* 仅当参数c持有的值不是enum light的成员时，此default才可达 */
      error_handler ( );
      break;
    }

}


  return res;

res = c; /* 不合规 - 此语句肯定是不可达的 */

}

Rule 2.2 不应有死代码

[IEC 61508-7 Section C.5.10], [ISO 26262-6 Section 9.4.5], [DO-178C Section 6.4.4.3.c]

类别：要求性（Required）

分析：不可判定（Undecidable），系统（System）

适用于：C90, C99

详述（Amplification）

任何被执行但其移除不会影响程序行为的操作构成死代码。由语言扩展引入的操作总被假定为对程序行为有影响。

注意：嵌入式系统的行为通常不仅由其动作的性质决定，也由它们发生的时间决定。

注意：不可达代码不是死代码，因为它无法执行。

注意：初始化与赋值操作不同，因此不是死代码的候选。

理由（Rationale）

死代码的存在可能表明程序逻辑中存在错误。由于死代码可能被编译器移除，其存在可能引起混淆。

例外（Exception）

假定转换为void表示有意不使用某个值。因此，该转换本身不是死代码。它被视为使用了其操作数，因此操作数也不是死代码。

示例

在本例中，假设p指向的对象在其他函数中使用。


extern volatile uint16_t v;
extern char *p;


void f ( void )

{

uint16_t x;

( void ) v; /* 合规 - 为访问v的副作用，void转换由例外允许 */

( int32_t ) v; /* 不合规 - 转换运算符是死的 */

v >> 3; /* 不合规 - >> 运算符是死的 */

x = 3; /* 不合规 - = 运算符是死的，x后续未被读取 */

*p++; /* 不合规 - * 运算符的结果未被使用 */

( *p )++; /* 合规 - *p被递增 */

}

在以下合规示例中，__asm关键字是语言扩展，不是函数调用操作，因此不是死代码：

__asm ( "NOP" );

在以下示例中，函数g不包含死代码，且本身不是死代码，因为它不包含任何操作。然而，对该函数的调用是死的，因为可以将其移除而不影响程序行为。


void g ( void )

{

/* 合规 - 此函数中没有操作 */

}


void h ( void )

{

g ( ); /* 不合规 - 此调用可以被移除 */

}

类别：要求性（Required）

分析：可判定（Decidable），单个翻译单元（Single Translation Unit）

适用于：C90, C99

如果注释开始序列/*或//出现在/*注释内部，很可能是由于缺少*/注释结束序列造成的。

Rule 3.2 不应在//注释中使用行拼接

类别：要求性（Required）

8.4 字符集和词法约定

Rule 4.1 八进制和十六进制转义序列应被终止

C90 [Implementation 11], C99 [Implementation J.3.4(7, 8)]

类别：要求性（Required）

分析：可判定（Decidable），单个翻译单元（Single Translation Unit）

适用于：C90, C99

详述（Amplification）

八进制或十六进制转义序列应被以下之一终止：

• 另一个转义序列的开始，或

• 字符常量的结束或字符串字面量的结束。

理由（Rationale）

如果八进制或十六进制转义序列后跟其他字符，存在混淆的可能。例如，字符常量'\\x1f'由单个字符组成，而字符常量'\\x1g'由两个字符'\\x1'和'g'组成。多字符常量表示为整数的方式是实现定义的。

如果字符常量或字符串字面量中的每个八进制或十六进制转义序列都被终止，混淆的可能性就降低了。

示例

在本例中，s1、s2和s3指向的每个字符串等价于"Ag"。


const char *s1 = "\x41g";          /* 不合规 */
const char *s2 = "\x41" "g";       /* 合规 - 由字面量结尾终止 */
const char *s3 = "\x41\x67";       /* 合规 - 由另一个转义序列终止 */


int c1 = '\141t';                  /* 不合规 */
int c2 = '\141\t';                 /* 合规 - 由另一个转义序列终止 */

类别：建议性（Advisory）

分析：可判定（Decidable），单个翻译单元（Single Translation Unit）

8.5 标识符

Rule 5.1 外部标识符应是不同的

C90 [Undefined 7], C99 [Unspecified 7; Undefined 28]

类别：要求性（Required）

分析：可判定（Decidable），系统（System）

适用于：C90, C99

详述（Amplification）

本规则要求不同的外部标识符在实现施加的限制内是不同的。

"不同"的定义取决于实现和正在使用的C语言版本：

• 在C90中，最低要求是外部标识符的前6个字符是有效的，但不要求其大小写有效；

• 在C99中，最低要求是外部标识符的前31个字符是有效的，每个通用字符或对应的扩展源字符占用6到10个字符。

在实践中，许多实现提供更大的限制。例如，C90中外部标识符通常是大小写敏感的，且至少前31个字符是有效的。

理由（Rationale）

如果两个标识符仅在非有效字符上有差异，行为是未定义的。

如果可移植性是关注点，使用标准中指定的最低限制应用本规则将是审慎的做法。

长标识符可能损害代码的可读性。虽然许多自动代码生成系统产生长标识符，但有充分理由将标识符长度保持在此限制以下。

注意：在C99中，如果扩展源字符出现在外部标识符中且该字符没有对应的通用字符，标准不规定它占用多少个字符。

示例

在以下示例中，定义都发生在同一个翻译单元中。相关实现支持外部标识符31个有效的大小写敏感字符。

/* 1234567890123456789012345678901********* 字符 */


int32_t engine_exhaust_gas_temperature_raw;     /* 不合规 */
int32_t engine_exhaust_gas_temperature_scaled;

/* 1234567890123456789012345678901********* 字符 */


int32_t engine_exhaust_gas_temp_raw;            /* 合规 */
int32_t engine_exhaust_gas_temp_scaled;

在以下不合规示例中，实现支持外部标识符6个有效的大小写不敏感字符。两个翻译单元中的标识符不同，但在其有效字符上不是不同的。

Rule 5.3 在内部作用域中声明的标识符不应隐藏外部作用域中声明的标识符

类别：要求性（Required）

分析：可判定（Decidable），单个翻译单元（Single Translation Unit）

适用于：C90, C99

详述（Amplification）

在内部作用域中声明的标识符应与外部作用域中声明的任何标识符不同。

"不同"的定义取决于实现和正在使用的C语言版本：

• 在C90中，最低要求是前31个字符有效；

• 在C99中，最低要求是前63个字符有效，每个通用字符或扩展源字符计为单个字符。

理由（Rationale）

如果标识符在内部作用域中声明但与外部作用域中已存在的标识符不是不同的，那么最内部的声明将"隐藏"外部的声明。这可能导致开发人员混淆。

注意：在一个命名空间中声明的标识符不会隐藏在另一个命名空间中声明的标识符。

术语外部和内部作用域定义如下：

• 具有文件作用域的标识符可被视为具有最外部作用域；

• 具有块作用域的标识符具有更内部的作用域；

• 连续的嵌套块引入更内部的作用域。

示例


void fn1 ( void )

{


  int16_t i;        /* 声明对象"i" */

{


    int16_t i;      /* 不合规 - 隐藏了先前的"i" */
    i = 3;          /* 可能令人困惑，不清楚这是指哪个"i" */

}

}


struct astruct { int16_t m; };
extern void g ( struct astruct *p );
int16_t xyz = 0;                            /* 声明对象"xyz" */


void fn2 ( struct astruct xyz )              /* 不合规 - 外部"xyz"现在被参数名隐藏 */

{

g ( &xyz );

}

uint16_t speed;


void fn3 ( void )

{


  typedef float32_t speed;                   /* 不合规 - 类型隐藏了对象 */

}

Rule 5.4 宏标识符应是不同的

分析：可判定（Decidable），单个翻译单元（Single Translation Unit）

适用于：C90, C99

详述（Amplification）

本规则要求，当定义宏时，其名称应与以下各项不同：

• 当前定义的其他宏的名称；以及

• 其参数的名称。

它还要求给定宏的参数名称彼此不同，但不要求两个不同宏的宏参数名称不同。

"不同"的定义取决于实现和正在使用的C语言版本：

• 在C90中，最低要求是宏标识符的前31个字符有效；

• 在C99中，最低要求是宏标识符的前63个字符有效。

如果两个宏标识符仅在非有效字符上有差异，行为是未定义的。由于宏参数仅在其宏展开期间有效，一个宏中的参数与另一个宏中的参数混淆是没有问题的。

如果可移植性是关注点，使用标准中指定的最低限制应用本规则将是审慎的做法。

长宏标识符可能损害代码的可读性。虽然许多自动代码生成系统产生长宏标识符，但有充分理由将宏标识符长度保持在此限制以下。

注意：在C99中，如果扩展源字符出现在宏名称中且该字符没有对应的通用字符，标准不规定它占用多少个字符。

  int32_t index;                 /* 合规 - "index"没有链接 */

Rule 6.1 位域应仅以适当类型声明

C90 [Undefined 38; Implementation 29], C99 [Implementation J.3.9(1, 2)]

类别：要求性（Required）

分析：可判定（Decidable），单个翻译单元（Single Translation Unit）

适用于：C90, C99

详述（Amplification）

适当的位域类型是：

• C90：unsigned int或signed int；

• C99：以下之一：

-- unsigned int或signed int；

-- 实现允许的另一个显式有符号或显式无符号整数类型；

-- _Bool。

注意：允许使用typedef来指定适当的类型。

使用int是实现定义的，因为int类型的位域可以是有符号或无符号的。

在C90中，不允许将enum、short、char或任何其他类型用于位域，因为行为是未定义的。

在C99中，实现可以定义在位域声明中允许的其他整数类型。

示例

以下示例适用于C90和不提供额外位域类型的C99实现。假设int类型是16位的。


typedef unsigned int UINT_16;
struct s {
  unsigned int b1:2;    /* 合规 */
  int          b2:2;    /* 不合规 - 不允许普通int */

UINT_16 b3:2; /* 合规 - typedef指定unsigned int */


  signed long  b4:2;    /* 不合规 - 即使long和int大小相同 */

};

类别：要求性（Required）

分析：可判定（Decidable），单个翻译单元（Single Translation Unit）

Rule 7.2 对所有以无符号类型表示的整数常量应添加"u"或"U"后缀

类别：要求性（Required）

分析：可判定（Decidable），单个翻译单元（Single Translation Unit）

适用于：C90, C99

详述（Amplification）

本规则适用于：

• 出现在#if和#elif预处理指令的控制表达式中的整数常量；

• 预处理后存在的任何其他整数常量。

注意：在预处理期间，整数常量的类型以与预处理后相同的方式确定，除了：

• 所有有符号整数类型的行为如同它们是long（C90）或intmax_t（C99）；

• 所有无符号整数类型的行为如同它们是unsigned long（C90）或uintmax_t（C99）。

理由（Rationale）

整数常量的类型是一个潜在的混淆来源，因为它依赖于多种因素的复杂组合，包括：

• 常量的大小；

• 整数类型的实现大小；

• 任何后缀的存在；

• 值表示的数制（即十进制、八进制或十六进制）。

例如，整数常量40000在32位环境中是signed int类型，但在16位环境中是signed long类型。值0x8000在16位环境中是unsigned int类型，但在32位环境中是signed int类型。

注意：

• 任何带有"U"后缀的值是无符号类型；

• 小于2^31的无后缀十进制值是有符号类型。

但：

• 大于或等于2^15的无后缀十六进制值可能是有符号或无符号类型；

• 对于C90，大于或等于2^31的无后缀十进制值可能是有符号或无符号类型。

常量的符号性应是显式的。如果常量是无符号类型，添加"U"后缀清楚地表明程序员理解该常量是无符号的。

注意：本规则不依赖于使用常量的上下文；可能应用于常量的提升和其他转换与确定本规则合规性无关。

Rule 7.3 小写字母"l"不应在字面量后缀中使用

类别：要求性（Required）

分析：可判定（Decidable），单个翻译单元（Single Translation Unit）

理由（Rationale）

分析：可判定（Decidable），单个翻译单元（Single Translation Unit）

适用于：C90, C99

详述（Amplification）

Rule 8.2 函数类型应采用带有命名参数的原型形式

C90 [Undefined 22–25], C99 [Undefined 36–39, 73, 79]

类别：要求性（Required）

分析：可判定（Decidable），单个翻译单元（Single Translation Unit）

适用于：C90, C99

理由（Rationale）

C语言的早期版本（通常称为K&R C [30]）没有提供对照相应参数检查参数数量或类型的机制。在K&R C中，对象或函数的类型不必声明，因为对象的默认类型和函数的默认返回类型是int。

C90标准引入了函数原型，这是一种声明参数类型的函数声明符形式。这允许对照参数类型检查参数类型。它还允许检查参数数量，除非函数原型指定期望可变数量的参数。出于与现有代码向后兼容的原因，C90标准不要求使用函数原型。出于同样的原因，它继续允许省略类型，在这种情况下类型默认为int。

C99标准从语言中移除了默认int类型，但继续允许K&R风格的函数类型，其中在声明中无法提供参数类型信息，在定义中提供参数类型信息是可选的。

参数和参数数量、类型以及函数的预期返回类型和实际返回类型之间的不匹配可能导致未定义行为。本规则以及Rule 8.1和Rule 8.4的目的是通过要求显式指定参数类型和函数返回类型来避免这种未定义行为。Rule 17.3确保在函数调用时可获得此信息，从而要求编译器诊断检测到的任何不匹配。

本规则还要求在声明中为所有参数指定名称。参数名称可以提供有关函数接口的有用信息，声明和定义之间的不匹配可能表明编程错误。

8.10.1 原理
