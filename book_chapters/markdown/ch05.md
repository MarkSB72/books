## 信息流说明

让我们考虑一个简单的嵌入式示例。设想 ECU 中有一个非常简单的温度监控组件（Temperature Monitoring Component（温度监控组件））。该系统从传感器读取温度，处理数据，然后通过向信息娱乐 ECU 发送 CAN 消息将温度显示在车辆仪表盘上。

为了将连续变化的模拟信号转换为软件可以理解的格式，嵌入式设备会使用模数转换器（ADC，Analog-to-Digital Converter）。ADC 周期性地将信号转换为数字值，并将其提供给用户，例如另一个软件模块。

抽象化后的 ECU 软件可能利用 ADC 外设来获取信号值（温度）。这个过程很可能由 ADC 读取软件模块处理。ADC 值需要进行滤波处理，滤波后的值将转发给温度转换软件模块（Temperature Conversion SW Module（温度转换软件模块））。这个特定的软件模块负责将滤波后的 ADC 值转换为物理温度值，最终呈现在显示模块上。

让我们熟悉各个软件模块及其角色：

- **ADC 读取模块（ADC Reading Module（ADC读取模块））：**读取 ADC 值，进行转换，并将其提供给温度转换 SWC。以下代码片段展示了在 AUTOSAR 环境之外如何实现这样的系统。它包含一个 `analog_to_digital` 函数，通过读取特定的 ADC 通道将模拟信号转换为数字信号。`adc_task_10ms` 任务从温度传感器获取模拟值，将其转换为数字值，并通过 `TCM_ProcessTemperature` 发送给温度处理模块：

```
#define ADC_RESOLUTION 1024 // Assuming a 10-bit ADC
#define TEMP_SEN_CHANNEL 2
int analog_to_digital(int channel) {
    // Convert analog value to digital
    int digital_value = (int)(rREG_ADC[channel].rawval * ADC_RESOLUTION);
    return digital_value;
}
void adc_task_10ms() {
    int digital_value=analog_to_digital(TEMP_SEN_CHANNEL);
    TCM_ProcessTemperature(digital_value);
}
```

- **温度转换模块（Temp Conversion Module（温度转换模块））：**接收数字值，应用校准和转换，为显示做准备。当温度发生变化时，它向显示模块发送请求，在车辆仪表盘上显示更新后的值。代码定义了一个函数用于处理从 ADC 读取模块获得的温度值，在需要时应用校准，并将更新后的温度值发送给显示模块。此过程避免了温度未变化时的冗余更新：

```
#define CALIBRATION_FACTOR 1.0
#define TEMPERATURE_CONVERSION_FACTOR 0.01
float current_temperature=0;
std_return TCM_ProcessTemperature (int digital_value) {
    float calibrated_value = digital_value * CALIBRATION_FACTOR;
    float temperature = calibrated_value * TEMPERATURE_CONVERSION_FACTOR;
    current_temperature = temperature;
    return(E_OK);
}
```

## 发送方-接收方通信

SR 接口管理 AUTOSAR 中 SWC 之间的数据交换。这些接口支持各种通信模式，包括 1-to-N 模型（一个发送方向多个接收方传输数据）和 N-to-N 模型（多个发送方向多个接收方传输数据）。有两种类型：

- **发送方（Sender，P Port）：**发出信息；接口通过提供端口引用

- **接收方（Receiver，R Port）：**等待接收信息；接口通过需求端口引用

---

例如，图 5.3 展示了一个 1-to-N 配置，负责计算车辆速度的 SWC（发送方）可以将此数据发送给多个其他 SWC（接收方）。这种数据交换可以是周期性的，也可以是事件驱动的：

![图5.3](images/p107_0.png)

图 5.3 – SR 1-to-N 示例

在 SR 接口的上下文中，数据元素（Data Element（数据元素））是信息交换的基本单元。你可以将数据元素想象为在 SWC 之间传输车辆速度、横摆率、加速度等信息的虚拟线路。虽然单个数据元素传输很常见，但 SR 接口足够灵活，可以容纳多个数据元素，允许更丰富、更全面的数据交换。

**关于数据元素：**为简单起见，你可以将 SR 接口中的数据元素视为一个全局变量，通过定义的接口可被多个 SWC 访问。一组数据元素可视为在组件间共享的结构化数据集。

例如，考虑一个测量速度的车载系统。一旦捕获到速度数据，它可以被发送给多个组件：一个组件可能用它来在仪表盘上显示当前速度；另一个可能用它来调整车辆的自适应巡航控制（Adaptive Cruise Control（自适应巡航控制））；第三个可能记录数据用于诊断目的。SR 接口的这种多播特性确保所有这些组件同时接收速度数据，并能在近乎实时的情况下对其做出响应。

### AUTOSAR XML（ARXML）建模

以下 ARXML 代码是作为示例提供的，旨在帮助你熟悉 ARXML 语法。它可能不完全准确，并且可能根据特定的 AUTOSAR Schema 而略有不同。

此 ARXML 片段定义了一个特定的 SR 接口，名为 `If_SR_SenderReceiverTest`，用于处理 `VehicleSpeed` 数据元素的发送或接收，类型为 `uint32`：

```
<SENDER-RECEIVER-INTERFACE UUID="2DABF647-F234-404A-9669-58A29FABF1BC">
  <SHORT-NAME>If_SR_SenderReceiverTest</SHORT-NAME>
  <IS-SERVICE>false</IS-SERVICE>
  <DATA-ELEMENTS>
    <VARIABLE-DATA-PROTOTYPE UUID="D1368B17-1925-4F77-B4A8-520A992CED1D">
      <SHORT-NAME>VehicleSpeed</SHORT-NAME>
      <SW-DATA-DEF-PROPS>
        <SW-DATA-DEF-PROPS-VARIANTS>
          <SW-DATA-DEF-PROPS-CONDITIONAL>
            <SW-CALIBRATION-ACCESS>NOT-ACCESSIBLE</SW-CALIBRATION-ACCESS>
          </SW-DATA-DEF-PROPS-CONDITIONAL>
        </SW-DATA-DEF-PROPS-VARIANTS>
      </SW-DATA-DEF-PROPS>
      <TYPE-TREF DEST="IMPLEMENTATION-DATA-TYPE">/AUTOSAR_Platform/ImplementationDataTypes/uint32</TYPE-TREF>
    </VARIABLE-DATA-PROTOTYPE>
  </DATA-ELEMENTS>
</SENDER-RECEIVER-INTERFACE>
```

作为开发人员，通常不会直接编写 ARXML 代码，但了解其基本格式对调试实现很有帮助。以下是解释：

- **<SENDER-RECEIVER-INTERFACE>：**该标签标记 SR 接口定义的开始
- **UUID：**唯一标识符，帮助将此接口与项目中的其他接口区分开
- **SHORT-NAME：**接口的可读名称
- **IS-SERVICE：**指示接口是否提供服务（服务导向通信通常为 true）或仅促进数据交换（SR 为 false）
- **<DATA-ELEMENTS>：**定义可通过接口传输的数据
- **<VARIABLE-DATA-PROTOTYPE>：**定义接口内的特定变量，有自己的 UUID 和名称
- **SW-CALIBRATION-ACCESS：**设为 NOT-ACCESSIBLE，表示数据不能通过标定工具修改（适用于只读传感器数据）
- **TYPE-TREF：**指定变量的数据类型，此处引用 uint32 类型

---

需求端口的 ARXML 语法示例与提供端口非常相似。不过，它将使用 `<R-PORT-PROTOTYPE>` 替代 `<P-PORT-PROTOTYPE>`，通信规范也将替换为 `<NONQUEUED-RECEIVER-COM-SPEC>`。在探索 ARXML Schema 时，你还会遇到队列通信规范如 `<QUEUED-RECEIVER-COM-SPEC>`，可以处理缓冲通信。

XML Schema 定义了 XML 文档的结构、内容和约束。在 AUTOSAR 中，ARXML Schema 遵循 XML Schema 的一般原则，但包括了建模汽车软件组件和接口的特定规则和结构。

## 通信类型

SR 接口可以以两种不同的方式使用：隐式（Implicit）和显式（Explicit）通信机制。

### 隐式 SR 通信

- **IMPLICIT_SEND（隐式发送）：**当运行实体使用 IMPLICIT_SEND 发布数据元素时，一旦运行实体结束，RTE 确保数据元素的最新值对接收方可用

- **IMPLICIT_RECEIVE（隐式接收）：**运行实体直接访问在其执行开始时已存在的数据元素值。传输的值存储在缓冲区中，因此在运行实体的生命周期内保持不变。图 5.4 的序列图说明了隐式 SR 接口的行为，其中 SWC B 发布数据，SWC A 接收数据：

运行实体 B 的优先级高于运行实体 A。因此运行实体 B 可以中断运行实体 A 并修改/读取数据。我们将在第 6 章探索 AUTOSAR 操作系统时介绍优先级和任务的概念。

![图5.4](images/p111_0.png)

图 5.4 – 隐式写入序列图

---

RTE API 的生成语法：

```
Rte_IRead : DataElementType Rte_IRead_<RunnableName>_<PortName>_<DataItemName>()
Rte_IWrite : Rte_IWrite_<RunnableName>_<PortName>_<DataItem>(DataElemementType Data)
```

其中 `DataElementType` 是数据类型，`Rte_IRead` 表示 RTE 读取函数，`<RunnableName>` 是执行读操作的运行实体名称，`<PortName>` 是读取数据的端口名称，`<DataItemName>` 是访问的特定数据项。例如，`float Rte_IRead_ReadSensorData_SensorPort_Temperature()`。

**隐式读取用例：**考虑一个在整个执行过程中需要一致温度数据的控制算法。当算法（运行实体）启动时，它读取初始温度值，该值被缓冲，控制算法在整个运行期间使用此稳定数据。

---

### 显式 SR 通信

- **EXPLICIT SEND（显式发送）：**数据更新后立即对所用用户发布，确保最新可用数据始终就绪
- **EXPLICIT RECEIVE（显式接收）：**显式调用转发到 RTE 以获取最新可用数据。传输值不被缓冲；运行实体读取数据元素时立即获取最新值

显式的发送方/接收方通信可以是有队列或无队列的，但两种方法都导致最新数据被立即发布和读取。可以将显式通信视为 RTE 中的一个全局缓冲区，发送方和接收方在执行读写操作时都可以访问它。

显式 RTE API 语法：

```
Rte_Read : DataElementType Rte_Read_<Runnable>_<Port>_<DataItem>()
Rte_Write : Rte_Write_<Runnable>_<Port>_<DataItem>(DataElemementType Data)
```

显式无队列变体使用 `Rte_Write` 和 `Rte_Read`。队列变体分别使用 `Rte_Send` 和 `Rte_Receive`。

**显式读取用例：**考虑一个监控电池电压的系统。监控系统需要按特定间隔检查电池电压以确保其在安全范围内。当监控系统（运行实体）发起电压检查时，它通过 RTE API 调用显式请求最新电池电压，从而在需要时获得最新数据。

## 客户端-服务器通信

通常缩写为 C/S 接口（Client-Server（客户端-服务器） Interface（客户端-服务器接口）），它促进 AUTOSAR 中 SWC 之间面向服务的通信。这些接口支持请求-响应通信模式，客户端向服务器发送服务请求，服务器处理请求并返回响应。例如，在客户端-服务器配置中，负责控制车辆灯光的 SWC（客户端）可以请求灯光状态或发送命令将其打开或关闭。服务器组件处理这些请求并提供必要的响应。这种交互可以是同步的（客户端等待服务器响应）或异步的（客户端继续处理并在稍后处理响应）。

- **客户端（Client，R Port）：**发起服务请求的组件，作为交互中的消费者
- **服务器（Server，P Port）：**响应客户端请求提供所需服务的组件，作为交互中的提供者

操作（Operation）是服务器提供的特定功能或服务。操作可以有参数（Argument），按方向分类：

- **Set（in）：**输入参数，为服务器提供必要数据
- **Get（out）：**输出参数，服务器处理后返回
- **双向（in-out）：**既能接收输入也能提供输出

**同步客户端-服务器通信：**客户端发送请求后等待服务器响应再继续。客户端在此期间被阻塞，无法执行其他任务。每个请求后立即获得响应，然后才能继续下一操作。适用于客户端需要立即获得结果的场景。

- SWC2 处理温度值后通过客户端-服务器接口请求 SWC3 显示

- SWC3 接收请求并使用 SR 接口通过 COM 模块发送 CAN 消息在仪表盘上显示温度

**如何选择：**选择 Provide 还是 Require 端口——取决于 SWC 是提供（Provide）还是消费/请求（Require）数据或服务。选择 SR 还是客户端-服务器接口——SR 适合持续数据更新而不需要响应的情况；客户端-服务器适合需要执行动作并期待结果/确认的情况。

此示例选择性地聚焦于 ADC 读取模块、温度转换模块和显示模块，特别说明如何使用接口提供 ADC 和温度值以及显示值。ADC 读取模块如何从驱动读取数据的详细设计超出了本次讨论的范围。目的是让你了解何时使用 SR 接口（如持续数据传输）和客户端-服务器接口（用于直接服务请求和响应）。

## 理解 AUTOSAR 中的事件

事件（Event）可以看作系统中可识别的发生或状态变化，可能需要相应的动作或反应。AUTOSAR 中的事件是触发系统内特定动作或反应的特定发生或条件。它们充当信号，通知 SWC 某个特定条件已满足，并促使其执行特定的功能。

事件不仅促进 SWC 之间的同步和通信，而且显著影响系统的整体性能和功能。本节将探讨端口、接口和事件之间的相互依赖关系，突出它们对 AUTOSAR 生态系统的综合影响。事件可以由各种源生成，如外部输入、定时器甚至其他 SWC，通常由专用的事件处理器或中断服务例程处理。

### 端口、接口和事件如何交互？

端口和接口定义了信息流的通道。然而，仅仅有这些通道还不够——我们需要一种机制基于接收到的信息或系统状态变化来触发动作。这就是事件发挥作用的地方。事件是与端口和接口关联的触发器，用于管理数据流或服务调用。

例如，当传感器检测到特定条件（如车门打开）时，可以生成一个事件。事件随后触发一系列动作，如打开车内灯。因此，事件是动作的触发器，在 AUTOSAR 中通常是运行实体。

考虑 ECU 中的一个抽象场景：温度传感器的 SWC（SWC 1）检测到温度急剧上升。传感器 SWC 通过其发送方端口使用 SR 接口周期性地发送温度数据。负责监控此数据的 SWC 2 中的主函数执行由定时事件触发的周期性检查。在一次周期性检查中，它检测到温度上升，立即使用客户端-服务器接口请求 SWC 3 进行紧急响应。此请求触发 SWC 3 中的事件，随即激活冷却系统。这个简化的示例说明了端口、接口和事件如何在 ECU 中协同工作以管理 SWC 之间的关键交互。
